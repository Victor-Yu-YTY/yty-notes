# PUB 集群大表归档 · 三步脚本与定时任务速查

> 配套文档：[MySQL大表归档](../项目经历/MySQL大表归档.md)（建表、检查项、逐晚判读等流程细节以那份为准）。
> 本文只回答两件事：**三步的脚本长什么样**、**谁在什么时间把它拉起来**。
>
> **脱敏说明**：集群域名、IP、DBA 账号、密码、库名前缀均已替换为占位符；表名保留真实归档表作示例。

| 占位符 | 原值类型 |
|--------|---------|
| `<PUB域名>` | PUB 集群 MySQL 接入域名 |
| `<归档库IP>` | 129 归档实例 IP |
| `<DBA账号>` / `<密码>` | 运维统一高权账号及其口令 |
| `db_xxx` | 库名已去掉品牌前缀、只留业务部分（如 `db_reports`、`db_call_center_v1`） |

## 〇、三步分别在解决什么

| # | 步骤 | 一句话作用 | 为什么不省 |
|---|------|-----------|-----------|
| 1 | **全量归档**（`archiver_pub_tmp.sh`） | 把历史存量数据边拷边删搬到归档侧，源表瘦下来 | 存量几千万行，靠每日增量永远追不上 |
| 2 | **表重建**（`mysql_pt_online_schema_change.sh`） | pt-osc 新建一张空表把剩余数据搬过去，替换原表 | InnoDB 删数据只释放页、**不归还操作系统**，不重建磁盘继续占着 |
| 3 | **每日增量**（`archiver_pub.sh`） | 每天 01:30 把当天过期的那一小段搬走 | 防止源表重新长回大表，让归档成为常态而不是一次性运动 |

**闭环链路**：夜间 tmp 全量窗口（5 小时/晚，跑几晚）→ 源表待归档量归零 → 白天低峰 pt-osc 重建回收空间 → 追加进每日增量 → 次日 `monitor.sh` 企微推送 ✅ 即该表全生命周期闭环。

## 一、全量归档 · `archiver_pub_tmp.sh`

**作用**：这是一个**一次只服务一张表**的临时脚本。用 `pt-archiver` 按 `--where` 圈出历史数据，一批 5000 行"先 INSERT 到归档侧、再 DELETE 源表"，逐批推进；`--run-time` 到点自动收工，第二天 cron 再拉起接着跑（幂等，不会重复）。

### 代码块①：主体脚本

```bash
#!/bin/bash
# 全量归档临时脚本：cron 每日 01:00 拉起，单晚窗口 5 小时
time=`date "+%Y%m%d"`

archiver_path=`which pt-archiver`
mysql_path="/opt/mysql/bin/mysql"
user=<DBA账号>
password=<密码>
port=3306
host=<PUB域名>            # 源库：PUB 集群
dest_host="<归档库IP>"     # 归档侧：129

echo "========== 开始执行单表 (RECONCILE_TTP_ACCOUNT) 边拷边删作业: $(date "+%Y-%m-%d %H:%M:%S") =========="

# 示例A：RECONCILE_TTP_ACCOUNT，保留 12 个月
# 该表 CREATE_TIME 无索引 → 不能用时间条件，改用「最大 ID 边界」一刀切，
# max_history_id 取边界时间对应的最大主键（归档量预估脚本可直接算出）
max_history_id=281014282
$archiver_path --source u=$user,p=$password,h=$host,P=$port,D=db_reconcile,t=RECONCILE_TTP_ACCOUNT \
--dest u=$user,p=$password,h=$dest_host,P=$port,D=db_reconcile,t=RECONCILE_TTP_ACCOUNT \
--no-check-charset --sleep 3 --analyze=ds \
--where="ID <= $max_history_id" \
--no-check-columns --progress=5000 --statistics --bulk-delete --txn-size=5000 --limit=5000 \
--run-time 18000 --replace \
>> /opt/mysql_archiver/arch_log/db_reconcile/RECONCILE_TTP_ACCOUNT_PURGE_$time.log

echo "========== 边拷边删作业结束: $(date "+%Y-%m-%d %H:%M:%S") =========="
```

**示例B：CREATE_TIME 有索引的表走动态时间条件**，与示例A只差 4 处（`--source`/`--dest` 表名、`--where`、日志路径），`max_history_id` 那行留着不用：

```bash
# DW_DEAL_INVITE_CALL，保留 6 个月；时间边界随执行日自动前推，走 IDX_CREATE_TIME 范围扫描
--source ... D=db_reports,t=DW_DEAL_INVITE_CALL
--dest   ... D=db_reports,t=DW_DEAL_INVITE_CALL
--where="CREATE_TIME<= date_sub(current_date(),INTERVAL 6 month)"
>> /opt/mysql_archiver/arch_log/db_reports/DW_DEAL_INVITE_CALL_PURGE_$time.log
```

### 对应定时任务

```cron
# 全量归档窗口：每日 01:00，跑完即停；换表时表名/日志路径跟着换
00 01 * * * /bin/bash /opt/mysql_archiver/archiver_pub_tmp.sh >> /opt/mysql_archiver/arch_log/db_reconcile/RECONCILE_TTP_ACCOUNT_cron.log 2>&1
```

### 关键参数口径

| 参数 | 取值 | 为什么 |
|------|------|--------|
| `--sleep 3` + `--limit/--txn-size 5000` | 每批 5000 行一个事务 | 控制单事务写入量，批间让主从与 IO 喘气 |
| `--run-time 18000` | 5 小时硬止损 | 凌晨必须收工，绝不拖进白天业务高峰 |
| `--bulk-delete` | 批量 DELETE | 比逐行删快一个量级 |
| `--replace` | INSERT…REPLACE | 重跑幂等，跑几晚都安全 |
| `--no-check-columns --no-check-charset` | 关校验 | 源表与归档表字符集/列顺序常有差异，开着必然报错退出 |
| `--analyze=ds` | 结束后收集统计 | 避免优化器拿着旧统计选错执行计划 |
| `--where` | 二选一 | 有时间索引用时间条件；没有就用 `ID <= max_history_id` |

## 二、表重建 · `mysql_pt_online_schema_change.sh`

**作用**：`pt-online-schema-change` 的通用包装器，按"集群 + 库 + 表 + DDL 片段"四个参数在线改表结构。全量归档后，源表虽然瘦了但**表空间文件没变小**，所以执行一次 `engine=innodb` 的空变更——pt-osc 建影子表、拷数据、原子 rename——空间真正归还操作系统；同时可顺带补索引（无 CREATE_TIME 索引的表，后续增量就靠这一步把索引补上）。

### 代码块②：主体脚本

```bash
#!/bin/bash
# 在线 DDL 通用脚本
# 用法: ./mysql_pt_online_schema_change.sh <集群> <库名> <表名> "DDL片段(不含 ALTER TABLE xx)"
# 支持集群：BOSS、CORE、PAI、PUB、AROUND、OPS、QITONG

db=$1; schema=$2; table=$3; ddl_value=$4

host=''
port=3306
user=<DBA账号>
password=<密码>

if [[ -n "$db" && -n "$schema" && -n "$table" && -n "$ddl_value" ]]; then
        # 集群 → 接入域名映射
        if   [[ "$db" = "BOSS" ]];   then host='<BOSS域名>'
        elif [[ "$db" = "CORE" ]];   then host='<CORE域名>'
        elif [[ "$db" = "PAI" ]];    then host='<PAI域名>'
        elif [[ "$db" = "PUB" ]];    then host='<PUB域名>'
        elif [[ "$db" = "AROUND" ]]; then host='<AROUND域名>'
        elif [[ "$db" = "OPS" ]];    then host='<OPS域名>'
        elif [[ "$db" = "QITONG" ]]; then host='<QITONG库IP>'
        fi

        begin_time=`date +'%Y-%m-%d %H:%M:%S'`
        log_time=`date +'%Y%m%d%H%M%S'`
        pt_online_log='/opt/hzs/log/'$db'_'$schema'_'$table'_'$log_time'.log'
        sql_ddl_exec_log='/opt/hzs/log/pt_online_change.log'   # 变更台账，永久保留

        # 执行变更
        /bin/pt-online-schema-change --host="$host" --port=$port --user="$user" --password="$password" \
          --alter-foreign-keys-method auto --no-version-check --no-check-replication-filters \
          --recursion-method=none --print --progress time,30 \
          --max-load Threads_running=50 --critical-load Threads_running=200 \
          --chunk-time 3 --sleep 15 --max-lag 300 \
          --set-vars "innodb_lock_wait_timeout=600" --charset utf8 \
          --alter "$ddl_value" D=$schema,t=$table --execute > $pt_online_log 2>&1

        end_time=`date +'%Y-%m-%d %H:%M:%S'`
        # 以日志里是否出现 Successfully 判定成败
        result=$(cat $pt_online_log | grep 'Successfully')
        if [[ "$result" != "" ]]; then result='Successfully'; else result='Failed'; fi
        echo '[ '$begin_time' ~ '$end_time' ] : '$schema','$table','$ddl_value','$result >> $sql_ddl_exec_log
else
        echo -e '请输入以下参数：\nDB集群：BOSS、CORE、PAI、PUB、AROUND、OPS、QITONG\nSCHEMA名称\nTABLE名称\nDDL语句（不含 ALTER TABLE xx 部分）'
fi
```

### 两种典型调用（真实归档表）

```bash
# 情况A 纯重建回收空间：CREATE_TIME 已有索引（如 DW_DEAL_INVITE_CALL）
/opt/hzs/scripts/mysql_pt_online_schema_change.sh PUB db_reports DW_DEAL_INVITE_CALL "engine=innodb"

# 情况B 重建 + 补索引一步到位：CREATE_TIME 无索引（如 SELL_CAR_PROGRESS_STEP_INFO，
# 补完索引每日增量才能用它做范围扫描）
/opt/hzs/scripts/mysql_pt_online_schema_change.sh PUB db_www SELL_CAR_PROGRESS_STEP_INFO "add index IDX_CREATE_TIME(CREATE_TIME)"
```

> 实操建议：放 `screen` 里跑（`screen -S osc_<表名>`），断开不影响；`screen -ls` 里会话消失即执行完毕。
>
> 时段选择：必须避开 01:00~06:00 的窗口（01:00 全量归档、01:30 每日增量、02:00 全库备份三者在这段重叠），改到白天低峰执行。

### 对应定时任务

重建通常是**按需手工触发**（挑白天低峰、单个表、需盯进度），因此 crontab 里默认是注释态；若确需批量定时执行，把日期改掉再开启：

```cron
# 定时执行在线 DDL 脚本，需要的时候开启
#00 02 24 09 * sh /opt/hzs/scripts/crontab_pt_online.sh
```

### 关键参数口径

| 参数 | 取值 | 为什么 |
|------|------|--------|
| `--chunk-time 3` + `--sleep 15` | 每拷 3 秒休息 15 秒 | 重建是最吃 IO 的操作，用比例限速压住复制延迟 |
| `--max-lag 300` | 复制延迟上限 300 秒 | 超阈自动暂停，保护从库/只读库 |
| `--max-load` / `--critical-load` | 50 / 200 | `Threads_running` 超 50 暂停，超 200 直接放弃 |
| `--recursion-method=none` | 不探测从库 | RDS 环境无 `SHOW SLAVE HOSTS` 权限 |
| `--no-check-replication-filters` | 跳过过滤检查 | 托管实例存在 binlog filter，不跳过会拒跑 |
| `--set-vars innodb_lock_wait_timeout=600` | 会话级锁等待 | 大表长事务避免中途报锁超时 |
| `--alter "engine=innodb"` | 逻辑空变更 | 借 pt-osc 的"建新表+拷数据+rename"完成真正的空间回收 |

## 三、每日增量归档 · `archiver_pub.sh`

**作用**：常驻的每日归档清单。一个脚本里串行排着几十个表块，每块独立一条 `pt-archiver` 命令，只搬"超过保留期"的那一小段数据，搬完源表保持小体量。**所有块一律用动态时间条件**（保留期随当天日期自动前推），不做固定 ID 切片。

两个落地去向：
- **同库保留**：目标端是同库的 `ARCHIVER_<表名>` 前缀表；
- **跨实例归档**：目标端是 129 归档实例的同名表，脚本头部 `dest_host` 决定。

> 自 2024-12-27 起取消 `--file` 参数：不再落地本地文本文件，直接写进归档库，少一跳、少占本地盘。

### 代码块③：主体脚本

```bash
#!/bin/bash
# 每日增量归档：cron 每日 01:30 拉起，逐表串行执行
time=`date "+%Y%m%d"`

archiver_path=`which pt-archiver`
mysql_path="/opt/mysql/bin/mysql"
user=<DBA账号>
password=<密码>
port=3306
host=<PUB域名>
dest_host="<归档库IP>"

# ---- 表1：NOTIFICATION_TARGET｜保留 1 个月｜同库 ARCHIVER_ 前缀表 ----
$archiver_path --source u=$user,p=$password,h=$host,P=$port,D=db_ms_notification,t=NOTIFICATION_TARGET \
--dest u=$user,p=$password,h=$host,P=$port,D=db_ms_notification,t=ARCHIVER_NOTIFICATION_TARGET \
--no-check-charset --sleep 1 --analyze=ds \
--where="CREATE_TIME<= date_sub(current_date(),INTERVAL 1 month)" \
--no-check-columns --progress=5000 --statistics --bulk-delete --txn-size=5000 --limit=5000 \
>> /opt/mysql_archiver/arch_log/db_ms_notification/NOTIFICATION_TARGET_$time.log

# ---- 表2：CALL_HISTORY_REQUEST｜保留 6 个月｜跨实例到 129 归档库｜--replace 保幂等 ----
$archiver_path --source u=$user,p=$password,h=$host,P=$port,D=db_call_center_v1,t=CALL_HISTORY_REQUEST \
--dest u=$user,p=$password,h=$dest_host,P=$port,D=db_call_center_v1,t=CALL_HISTORY_REQUEST \
--no-check-charset --sleep 1 \
--where="CREATE_TIME<= date_sub(current_date(),INTERVAL 6 month)" \
--no-check-columns --progress=5000 --statistics --bulk-delete --txn-size=5000 --limit=5000 --replace \
>> /opt/mysql_archiver/arch_log/db_call_center_v1/CALL_HISTORY_REQUEST_$time.log

# ---- 表3：BI_RUNTIME_TASK｜保留 12 个月｜大表，开 --analyze=ds 刷新统计 ----
$archiver_path --source u=$user,p=$password,h=$host,P=$port,D=db_bi_schedule,t=BI_RUNTIME_TASK \
--dest u=$user,p=$password,h=$dest_host,P=$port,D=db_bi_schedule,t=ARCHIVER_BI_RUNTIME_TASK \
--no-check-charset --sleep 1 --analyze=ds \
--where="CREATE_TIME<= date_sub(current_date(),INTERVAL 12 month)" \
--no-check-columns --progress=5000 --statistics --bulk-delete --txn-size=5000 --limit=5000 \
>> /opt/mysql_archiver/arch_log/db_bi_schedule/BI_RUNTIME_TASK_$time.log
```

**变体：按主键固定条数推进**（仅当时间字段不适合做边界、或单日增量过大需限流时使用；脚本里以注释形式留档）：

```bash
# 每天固定归档 170000 条：取当前最小 id，切到 id + 170000
begin_id=`$mysql_path -h$host -P$port -u$user -p$password -NBe 'select min(id) from db_call_center_v1.CALL_SOUND;'`
end_id=$((begin_id + 170000))
$archiver_path --source ... t=CALL_SOUND \
--dest ... --where="id >= $begin_id and id < $end_id" ...
```

### 对应定时任务

```cron
30 01 * * * /bin/bash /opt/mysql_archiver/archiver_pub.sh >> /opt/mysql_archiver/archiver_pub.log 2>&1
```

## 四、闭环验收

| 检查点 | 命令 / 现象 |
|--------|------------|
| 全量当晚跑了多少 | `tail -30 /opt/mysql_archiver/arch_log/<库>/<表>_PURGE_$(date +%Y%m%d).log`，看 statistics 行数、`EXIT STATUS 0` |
| 全量是否跑完 | 源表待归档量逐晚递减，归零即可进重建 |
| 重建是否成功 | `echo $?` + `tail /opt/hzs/log/pt_online_change.log` 出现 `Successfully`；行数与重建前一致；情况B 用 `SHOW INDEX` 确认 `IDX_CREATE_TIME` 已存在 |
| 增量是否闭环 | 次日 09:30 企微推送出现 `✅ <表名>_YYYYMMDD.log : 归档成功`。monitor.sh 按 `arch_log/**/*_当天日期.log` 命名规则扫描，**日志文件名必须严格符合规则**，否则该表等于没被监控 |
| 空间是否回收 | 巡检/监控侧观察表大小曲线下跌 |
