# 从「命中即发」到「工作日汇总一封」：一次夜间告警邮件自动化的完整实践

> 项目周期：约 1 天（含需求变更与一次硬核排障）
> 技术栈：Python 3.6（纯标准库）、Grafana Alerting API、SMTP/SSL、cron、Shell
> 关键词：告警治理、邮件网关解析 bug、旁路只读集成、可在生产安全落地的脚本工程

> **脱敏说明**：本文中的域名、IP、主机名、邮箱、账号与凭据均已替换为示例值，内部规则/大盘标识符以占位符表示；技术细节、排查思路与代码逻辑保持原样。

---

## 一、需求是什么样的

公司内部有一套基于 Grafana Alerting 的告警体系，其中一条规则监控某数据库集群的**用户连接数**，只在凌晨时段（服务端查询里写死了时间窗口）可能触发。

最初的诉求很朴素：

> 每天 **00:00–03:00** 之间，如果出现这条告警，就把告警详情**发一封邮件**给值班同事，提醒他处理。白天不打扰。

项目推进到一半，需求方追加了变更：

1. 不再"命中即发"，改成 **凌晨只记录，工作日（周一至周五）10:00 把这一批告警整合成一封**发出；
2. 邮件主题去掉尾部的 `(IP:端口)`，也不要有"等 N 条"这类计数后缀；
3. 正文把动作要求「请进行代码重发」**突出显示**；
4. 发件人换成专用的服务邮箱，收件人之外增加两个抄送。

另外还有几条不成文的硬约束：

- **不能改动任何 Grafana 告警规则与通知策略**（生产链路，动它风险极高）；
- 不能在业务群里 @人（有过明确要求）；
- 只读取告警数据，全程不写任何配置。

## 二、方案选型：为什么走「旁路只读 + 自己发信」

需求最容易想到的两条"捷径"，都被我否掉了：

| 方案 | 为什么不用 |
|---|---|
| **监听业务群里的告警消息**，命中后再转发 | 企业微信群机器人是**单向**的，读不到群消息；要读群消息只能走"会话内容存档"（需要企业购买许可 + 管理员审批）或"机器人回调"（只能收到 @ 它自己的消息）。技术上成本极高、稳定性差，还依赖群不刷屏。 |
| **在 Grafana 里加一条通知策略**，把这条规则路由到邮件 | 需要改动**生产告警链路**；而且通知策略上的静默时段（mute timing）存在时区语义坑，很容易把"只提醒 0–3 点"配错。邮件正文的定制能力也受限。 |

最终采用的方案：**旁路轮询 + 自己发信**。

```
cron（只在收集窗口与汇总窗口触发）
   └─ Shell 包装脚本（载入凭据 → 调用主程序）
        ├─ GET  /api/alertmanager/grafana/api/v2/alerts     ← 只读，不写任何配置
        ├─ 过滤：告警名匹配 + 状态 active + 未被静默/抑制
        ├─ 收集窗口（00:00–03:00）：命中的告警写入"待汇总队列"，不发信
        └─ 汇总窗口（工作日 10:00）：把队列整合成一封邮件发出
```

这个方案的取舍很清楚：

- **优点**：零权限依赖、不动生产链路、随时可停、正文格式完全可控；
- **代价**：有轮询延迟（分钟级）、需要一台常驻机器、需要自己维护去重与状态。

对本场景（夜间告警 + 上午汇总）来说，这几条代价都可以接受。

## 三、实现要点

### 3.1 时间与窗口

- 所有时间判定使用**固定 UTC+8 偏移**（`timezone(timedelta(hours=8))`），**不依赖服务器时区与 tzdata**——国内无夏令时，固定偏移既准确又免依赖；
- 窗口采用**左闭右开**：`00:00:00 ≤ now < 03:00:00`，即 03:00 整点不算窗口内；
- 汇总时段的判定同理：`10:00 ≤ now < 10:10`（留 10 分钟重试窗口），并额外要求"工作日 + 当天尚未发过"。

### 3.2 两种发送模式，配置一行切换

```ini
; digest  : 窗口内只收集，工作日 10:00 汇总一封（当前需求）
; realtime: 命中即发（旧行为，保留可随时切回）
send_mode = digest
digest_at = 10:00
digest_weekdays_only = true
; pending = 自上次汇总以来全部（周末凌晨的告警会在周一 10:00 一并发出，不丢告警）
; today   = 只汇总当天凌晨（周末凌晨的告警将被丢弃）
digest_scope = pending
```

### 3.3 汇总状态机

状态文件（JSON）里保存一个"待汇总队列"：

```json
{
  "pending": {
    "<fingerprint>": {
      "alertname": "...", "user": "svc_user", "instance": "10.0.0.11:9297",
      "summary": "...", "detail": "用户 ... 当前连接数为 6，已超过阈值 4。...",
      "count": 3,
      "first_time": "2026-09-15 00:42:10", "last_time": "2026-09-15 01:12:30",
      "date": "2026-09-15", "last_date": "2026-09-15"
    }
  },
  "meta": { "last_digest_date": "2026-09-15", "last_digest_count": 1 }
}
```

几条关键设计：

- **同一告警多次命中只记一条**（按 fingerprint 合并），累计次数、保留最新详情与首末时间——这样既不会被刷屏，又能看出"这是持续问题还是瞬时抖动"；
- **发出成功后才清队列**，并记录 `last_digest_date`，保证"当天不重复发"；
- **队列为空则静默不发**（不制造"无告警"的噪音邮件）；
- **dry-run 刻意不清队列、不标记已发**——否则一次演练会把真实数据吃掉，这是很多脚本容易忽略的坑。

### 3.4 并发与幂等

cron 每分钟触发，存在上一轮未结束就再次启动的可能，所以：

- 用**文件锁**（`O_CREAT|O_EXCL` + 陈旧锁接管）保证同一时刻只有一个实例在跑；
- 状态文件**原子写入**（临时文件 + `os.replace`）；
- 单次发送数量设上限，超出的下轮继续（不丢）。

### 3.5 安全与可观测

- 所有密钥（Grafana 凭据、SMTP 授权码）**不入代码仓库、不入配置文件**，放在 `/etc/sysconfig/<name>`（`chmod 600`），由包装脚本 `source` 后传给程序；
- 日志与状态文件 `chmod 600`（里面有用户名、内网地址这类明细）；
- `--print-config` 打印配置时**只显示"是否已配置 + 长度"**，不泄露任何字符；
- 日志按 5MB × 3 轮转；另有可选**每日心跳邮件**（只发给维护者），写明"昨夜收集了几条、汇总发没发"——不用翻日志就知道程序是否还活着。

## 四、排查实录：几个真实的坑

这一节是全文最有价值的部分——需求本身不复杂，**真正耗时间的是环境与链路里的意外**。

### 4.1 头号问题：企业邮箱网关把邮件「拆坏」了

**现象**：程序报告发送成功，收件人也能收到，但邮件显示成这个样子——

```
Subject: =?utf-8?b?44CQ5aSc6Ze0?=
 =?utf-8?b?5ZGK6K2m5o+Q6YaS44CR...?= ...（多段编码字）
Content-Type: text/plain; charset="utf-8"
Content-Transfer-Encoding: quoted-printable
MIME-Version: 1.0

=E9=82=B1=E9=87=91=E6=9D=B0=EF=BC=8C=E4=BD=A0=E5=A5=BD=EF=BC=9A...
```

即：**主题是一串 `=?utf-8?b?` 编码字，正文是一堆头部 + 编码后的正文**。

**排查过程**（关键是分层，别一口咬定是某一层的问题）：

1. **先证明"生成端"没问题**：把原始报文解码，内容完全正确——说明邮件本身是合规的；
2. **再证明"发送端"没问题**：写了一个假的 SMTP 类截获 `smtplib` 实际写出的字节，确认全部使用 CRLF、头部连贯、`From` 之后没有异常空行；
3. **拿到"传输端"的证据**：把收件箱里的邮件导出为 `.eml` 逐字节分析，发现——
   - 真实头部里只有网关自己加的一串 `X-*` 头，加上我们的 `From:` 一行；
   - 我们**其余的头部（To/Subject/Date/Message-ID/Content-Type/MIME-Version）全部被塞进了正文**；
   - `Message-ID` 被中间系统加了前缀改写。
4. **单变量二分定位**：发三封对照邮件，一次只改一个因素：

| 实验 | 发件人显示名 | 主题/正文 | 结果 |
|---|---|---|---|
| T1 | ASCII | ASCII | ✅ 正常 |
| T2 | **中文（RFC 2047 编码字）** | ASCII | ❌ **被拆坏** |
| T3 | ASCII | **中文** | ✅ 正常 |

**根因**：该邮件网关在处理 **`From` 里含编码字（encoded-word）的显示名**时解析异常——它把显示名之后的头部整体当成了正文。中文主题、中文正文本身完全没问题。

**修复**：把发件人显示名固定为**纯 ASCII**（如 `alert-bot`），中文只出现在主题与正文里。同时在代码里加了防呆：一旦检测到显示名含非 ASCII 字符，发信前打印明确告警；并补了回归断言把这个约束锁死。

**经验**：
- "邮件显示乱码"这类问题，**先分层定位**（生成端 → 传输端 → 客户端），不要一上来就改编码；
- **字节级证据**（截获发送字节 + 导出 .eml 分析）比任何猜测都可靠；
- **一次只改一个因素的对照实验**，能在十几分钟内把范围从"玄学"收敛到一个明确字段。

### 4.2 Grafana ruler API 的两个"反直觉"

- 规则列表接口返回的是 **map（namespace → 规则组数组）**，不是数组——按数组遍历会直接报错；
- Grafana 10.x 里规则的标题不在顶层 `title`，而是嵌在 **`grafana_alert.title`** 里。

排查这类问题的通用做法：把接口原始响应打出来（只看类型和前几百字节），比反复猜字段名快得多。

### 4.3 Python 3.6 环境适配

目标机只有 Python 3.6，而 `datetime.fromisoformat` 是 3.7 才引入的，脚本直接抛 `AttributeError`。

修复方式：**自己写一个正则版 RFC3339 解析器**（支持 `Z`、`+08:00`、毫秒、无时区按 UTC 处理），彻底不依赖该 API；同时在文件开头加了版本闸门，低于 3.6 时直接给出人话提示而不是晦涩的 ImportError。

顺带补了 5 个时间格式的边界用例——**一次适配顺手换来一组回归测试**。

### 4.4 打码反而泄露了信息

最初 `--print-config` 的打码是"保留首尾各 2 个字符"，结果日志里留下了 `Yu********14` 这样的痕迹。而日志是要长期留存、可能被归档的。

改成**只输出"是否已配置 + 长度"**（`<已配置，长度 12>`），并加了断言：`mask('abcdefgh')` 的结果里不允许出现任何原字符。

### 4.5 小细节也有代价

- **`Message-ID` 的域名不合法**（用了非域名形式）——部分邮件网关会判为可疑。改成取发件人真实域名，拿不到再退化为 `localhost`；
- **CLI 参数只在部分代码路径生效**：`--cc` 覆盖一开始只接在"自测/样例"路径上，主流程（cron 走的那条）没接，导致"观察期只发给自己"时仍会按配置抄送给别人。修完后补了两条断言（传空数组不抄送 / 不传则按配置抄送），把"参数必须在所有路径生效"这件事固化下来；
- **正文编码**：从 `base64` 换成 `quoted-printable`（7-bit 安全、对邮件网关更友好），并做成可配置项（`quoted-printable / base64 / 8bit / auto`）。

### 4.6 部署环节：用哈希校验抓出「文件传旧了」

因为是"本地开发 → 跳板机上传 → 安装到运行目录"，中间隔着两次人工操作，**两次**出现"代码是新的、配置还是旧版"的情况：

```
期望: c5d3780d1ec9001a  config/app.conf
实际: 3f18556b7b3a331e  config/app.conf   ← 上一版
```

第一次还踩了"大小写"的坑：本地 Windows 的 `Get-FileHash` 输出大写、Linux 的 `sha256sum` 输出小写，导致 diff 误报。

做法固定为：**每次安装前先对 `sha256sum`，对不上就不继续**。为了确认"到底哪一版"，还写了个"回退脚本"——把本版改动反向替换回去，看哈希是否正好等于现场那个值，从而**用数学方式证明**是文件旧了，而不是靠猜。

### 4.7 cron 相关的三个坑

| 坑 | 说明 |
|---|---|
| `%` 必须转义 | crontab 里 `%` 有特殊含义，`date +%Y%m%d` 要写成 `date +\%Y\%m\%d` |
| cron 的 PATH 很精简 | 包装脚本里显式定位解释器（`command -v python3`，拿不到就回落到 `/usr/bin/python3`） |
| 别用编辑器改 crontab | 用"导出 → 追加 → 整体载入 → `diff` 校验"的非交互流程，比在 vi 里手改安全得多，而且能证明"原有任务一条没丢" |

```bash
crontab -l > /root/cron.bak.$(date +%Y%m%d%H%M)
cp "$(ls -t /root/cron.bak.* | head -1)" /root/cron.new
cat >> /root/cron.new <<'EOF'
* 0-2 * * * /bin/bash /opt/scripts/<db>/run_notify.sh >> /opt/scripts/<db>/logs/cron_$(date +\%Y\%m\%d).log 2>&1
0-10 10 * * 1-5 /bin/bash /opt/scripts/<db>/run_notify.sh >> /opt/scripts/<db>/logs/cron_$(date +\%Y\%m\%d).log 2>&1
EOF
crontab /root/cron.new
diff "$(ls -t /root/cron.bak.* | head -1)" <(crontab -l)   # 只应出现新增行（>），不能有丢失行（<）
```

## 五、验证体系：怎么证明它真的对

因为这东西"半夜才可能触发"，靠人工观察是不可行的，所以验证全部前移：

| 层次 | 手段 | 覆盖什么 |
|---|---|---|
| 逻辑 | **离线自测 90 项断言** | 窗口边界（含 03:00 整点）、时区换算、用户解析、认证解析、打码、收件人/抄送信封、正文编码、Message-ID、去重与锁、汇总状态机、跨周末归属 |
| 配置 | `--print-config`（密钥打码） | 配置真的被读进来了 |
| 链路 | `--check-smtp`（**只连不发**） | SMTP 出网、端口、授权码、发件人一致性 |
| 端到端 | `--send-sample` / `--send-sample-digest`（发给操作者自己） | 渲染 + SMTP + 真实投递，且不打扰真实收件人 |
| 观察期 | cron 先挂 `--dry-run` | 用真实数据演练，但不产生任何邮件 |
| 交付确认 | 导出 `.eml` 逐字节分析 | 确认最终到达的报文结构正确 |

其中"**只连不发的 SMTP 自检**"和"**把样例邮件发给自己**"这两个设计特别省事：前者把认证问题隔离出来，后者在真实告警不触发的白天也能把整条链路跑通。

## 六、最终效果

### 6.1 汇总邮件长这样（示意）

```
Subject: 【夜间告警提醒】GP集群用户连接数超标 - 用户 svc_user

值班同事，你好：

【请进行代码重发】

以下为夜间监控窗口（每日 00:00-03:00，北京时间）命中的告警汇总，共 2 条：

覆盖日期：2026-09-15 ~ 2026-09-16

========================
[1] 在线账号连接数
用户：svc_user    实例：10.0.0.11:9297    级别：critical
触发时间：2026-09-15 00:42:10（最后一次 2026-09-15 01:12:30）    累计命中 3 次
告警摘要：GP集群用户连接数超标
告警详情：用户 svc_user 当前连接数为 6，已超过阈值 4。请立即检查该用户是否存在慢查询或连接泄漏。
========================
[2] 在线账号连接数
...
========================

规则详情：https://grafana.example.com/alerting/grafana/<rule-uid>/view

（本邮件为汇总邮件，由自动化程序于 2026-09-16 10:00:05 发出；监控窗口 每日 00:00-03:00，工作日 10:00 汇总发送）
```

### 6.2 运行节奏

| 时间 | 行为 |
|---|---|
| 每天 00:00–02:59 | 每分钟轮询一次，命中即入队；**不发任何邮件** |
| 工作日 10:00–10:10 | 队列非空 → 整合一封发出（发出后当天不再重复）；队列为空 → 静默 |
| 周五凌晨命中 | 周五 10:00 就发（周五是工作日） |
| 周六/周日凌晨命中 | 累积到**周一 10:00** 一并发出（不丢告警） |
| 每天 10:05（可选） | 给维护者发一封心跳邮件，汇报"收集了几条、汇总发没发" |

### 6.3 交付物

```

├── notify_main_test.py       # 离线自测（90 项断言）

├── data/notify_state.json    # 去重与待汇总状态（600）
└── logs/notify.log           # 运行日志（600，5MB×3 轮转）
/etc/sysconfig/<name>         # 密钥（600）
```

## 七、复盘：几条可以复用的经验

1. **触发源要选告警系统，不要选"群消息"**。读群消息的成本和不确定性远高于直接读告警 API，而且直接读源头天然会尊重静默与抑制。
2. **时间窗判定用固定偏移，不要依赖服务器时区**。这条规矩能避免一大批"凌晨窗口莫名其妙偏移"的诡异问题。
3. **邮件类问题要分层定位 + 留字节级证据**，并且用"一次只改一个因素"的对照实验收敛范围。这次的根因（网关对 `From` 编码字的解析 bug）就是靠三封对照邮件在几分钟内锁定的。
4. **部署必须做哈希校验**。人工中转的操作链越长，越要假设"文件可能不是你以为的那一份"。
5. **dry-run 必须是无损的**：不清队列、不标记已发，否则一次演练就会吃掉真实数据。
6. **参数要在所有代码路径生效**，并写测试锁住——"只在自测路径生效"这种 bug 很隐蔽。
7. **安全按"日志会被归档"的标准做**：密钥外置、日志与状态 600、打码不泄露任何字符。
8. **需求变更时，测试断言也是需求的一部分**——这次改主题格式/动作语时，正是因为断言写死了旧文案，才立刻暴露出"哪里还没同步改"。
9. **给"半夜才可能触发"的任务配一个心跳**，比任何监控都省心。
