# 一、项目背景

## 1.1 系统概况（脱敏）

| 代号 | 角色 | 说明 |
| --- | --- | --- |
| **DB-A** | 数据库实例 A | 备份体积较大（约 460 GB/份），承担某监控类业务 |
| **DB-B** | 数据库实例 B | 备份体积较小（约 180 GB/份），测试环境从库 |
| **STOR-SRV** | 网络存储服务器 | 提供 NFS 导出，容量 2 TB，**被 DB-A 与 DB-B 共同挂载使用** |
| **堡垒机** | 运维入口 | 所有服务器操作统一经堡垒机，会话录屏 + 命令审计 |

**备份方式**：基于 `xtrabackup` 的 MySQL 全量物理热备。

**调度方式**（`crontab`）：

| 实例 | 备份执行 | 告警检查 |
| --- | --- | --- |
| DB-A | 每周一、周四 **03:00** | 每周一、周四 **09:00 / 15:00** |
| DB-B | 每周一、周四 **01:00** | 每周一、周四 **09:00 / 15:00** |

> 两台机器**故意错开 2 小时**，避免同时向同一块共享存储写入造成峰值叠加。

**存储挂载关系**：

```
STOR-SRV 的 NFS 导出  ──┬──►  DB-A 的 /data2  ──►  /data2/mysql_backup/env-a
    （2 TB，共用）       └──►  DB-B 的 /data2  ──►  /data2/mysql_backup/env-b
```

> **关键架构特征**：两台实例的备份落在**同一块物理存储**上，空间互相挤占。
> 在任一台上执行 `df -hT /data2`，看到的是**两台机器的总和**。

## 1.2 项目触发点

运维侧收到一条备份失败告警，要求排查"两台线下机器备份频频失败"的问题。
接手时对现场**完全不了解**：不知道备份脚本在哪、不知道备份时间、不知道上次失败是什么时候、也不知道失败原因。

# 二、需求说明

## 2.1 原始需求

| 编号 | 需求 | 类型 |
| --- | --- | --- |
| **R1** | 备份保存策略由"同时存在约 2 份"改为**同时只存在 1 份** | 业务需求 |
| **R2** | 写文件**之前**增加空间判断：<br>• 剩余空间**足够**支撑一次新备份 → 维持原流程（**先备份，成功后再删旧**）<br>• 剩余空间**不足** → **先把旧备份删掉，再执行备份** | 业务需求 |
| **R3** | 两台机器的备份脚本**都要改** | 范围要求 |

## 2.2 排查后追加的需求

排查过程中发现的问题，追加为整改需求：

| 编号 | 需求 | 来源 |

| **R7** | 保留排障证据（日志保留期需延长） | 早期失败证据已被自动清理，无法追溯 |

# 三、排查过程

## 3.1 排查方法论

本次排查遵循以下原则，事后证明每一条都起了作用：

| 原则 | 说明 |
| --- | --- |
| **① 只读优先** | 全程**不执行**任何写操作（不跑备份脚本、不删文件、不改配置），直到方案确定 |
| **② 先建基线** | 动手前先把"任务在哪、什么时候跑、产物在哪、日志在哪"全部摸清 |
| **③ 多源交叉验证** | 同一个结论至少用**两个独立证据源**印证（脚本日志 / 调度器日志 / 产物时间戳 / 告警记录 / 进程启动时间）|
| **④ 警惕"看起来没问题"** | 曾因"目录大小与往期一致"错误推断某次失败为成功，事后更正 |
| **⑤ 追到"为什么没人发现"** | 不只查"为什么失败"，还要查"为什么失败没被告警" |
| **⑥ 量化** | 把现象算成数字（占用率、峰值、余量），才能判断是否必然发生 |
| **⑦ 生产操作留底** | 任何修改前先 `cp -a` 备份原文件并记录哈希 |

## 3.2 阶段一：摸清备份机制（只读）

**目标**：回答"备份是什么、什么时候跑、脚本在哪"。

**做法**：按"定时任务 → 脚本路径 → 产物与日志目录"的顺序逐层收敛。

**产出**：

| 问题 | 答案 |
| --- | --- |
| 备份机制 | `xtrabackup` 全量物理热备，由 `crontab` 触发 |
| 备份时间 | DB-A：周一/周四 03:00；DB-B：周一/周四 01:00 |
| 脚本位置 | 两台均为 `/data/backup/mysql_backup.sh` |
| 告警脚本 | DB-A：`mysql_backup_monitor.sh`；DB-B：`mysql_beifen_alter.sh` |
| 产物与日志 | `${BASE_PATH}/data/YYYYMMDD/` 与 `${BASE_PATH}/log/YYYYMMDD/*.log` |
| 备份目标 | 共享 NFS（2 TB，两台共用）|

**关键发现**：DB-A 与 DB-B 的备份脚本**内容已经分叉**（DB-B 有超时参数恢复的 `trap`，DB-A 没有）——
说明两台脚本是"手工复制 + 各自演化"的产物，这为后续的监控行为差异埋下伏笔。

## 3.3 阶段二：还原失败时间线（多源交叉验证）

**目标**：回答"上次失败是哪一次、失败在什么阶段"。

**做法**：由于备份日志的保留策略是"超过 5 天即删"，机器上只剩最近 2 份日志，因此**必须结合多种证据源**：

| 证据源 | 作用 |
| --- | --- |
| 备份脚本自身日志 | 记录成功/失败状态行、清理动作 |
| 产物目录的修改时间 | 反映"上次成功产出" |
| 存储上残留的中间文件 | 反映"某次运行在哪个阶段中断" |
| 监控告警记录 | 反映"哪一天被系统判定为失败" |

**核心判定技巧**：脚本的过期清理动作**只写在成功分支之后**，失败时会直接退出、跳过清理。
因此——

> **日志中出现"Removing ..."清理记录，即证明该次备份的执行流程走到了成功分支。**
> 反过来，如果某天只有"失败"而没有任何清理记录，说明该次运行在备份阶段就中断了。

据此逐日核对，确认了 3 起失败案例。

## 3.4 阶段三：识破一次严重误判（**方法论的转折点**）

**误判过程**：

某次失败的产物目录大小为 **约 180 GB**，与历次**正常备份的目录大小完全一致**。
据此初步判断"这次备份是成功的"，转而怀疑其他方向。

**更正过程**：

拿到该日的完整日志后，末段显示：

```
Executing FLUSH NO_WRITE_TO_BINLOG BINARY LOGS
xtrabackup: Unknown error 1160
xtrabackup: Unknown error 1158
[ERROR] failed to execute query 'FLUSH NO_WRITE_TO_BINLOG BINARY LOGS'
        : 2013 (HY000) Lost connection to MySQL server during query
#################  mysql full_backup failed  ####################
```

**这是一次失败。** 原因是备份在**最后一步**才中断，而 `xtrabackup` 的数据文件拷贝阶段**早已全部完成** ——
所以目录大小"看起来完整"，实则**缺少收尾文件、完全不可用于恢复**。

**沉淀出的判定规则**（已写入整改后的运维规范）：

> **判断备份成功，只能看日志中的成功状态行。**
> - **目录存在 ≠ 成功**（脚本启动时就会先创建目录）
> - **目录大小相同 ≠ 成功**（最后一步失败时，数据文件已全部拷完）
>
> 相关计数验证：失败案例中，该废目录的字节数与正常备份**误差在 1% 以内**。

## 3.5 阶段四：追查"为什么失败没人发现"

**目标**：这起失败持续了一整天，为什么没有任何告警？

**做法**：反查告警脚本的判定逻辑。

**发现**：

告警脚本的判定方式是 **取备份日志的最后一行做字符串匹配**：

```sh
LAST_LINE=$(tail -n 1 "$LOG_FILE")            # 只看【最后一行】
case "$LAST_LINE" in
  *"...failed"*)   CUR_STATUS="failed"  ;;
  *"...succeed"*)  CUR_STATUS="success" ;;
  *)               CUR_STATUS="success" ;;    # 兜底：判成成功
esac
```

而 DB-B 的备份脚本在退出时，**最后写入日志的是一行超时参数恢复的提示信息**（由 `trap` 触发），
把真正的"失败"状态行**覆盖**掉了：

```bash
trap '
    save_log "Restoring original global timeout parameters..."   # ← 覆盖状态行
    mysql ...恢复超时参数...
    rm -f $TEMP_CNF
' EXIT
```

**结果**：

| 实际情况 | 日志最后一行 | 告警脚本判定 |
| --- | --- | --- |
| 备份成功 | `Restoring ...` | 匹配不到 → 兜底 → **success** ✅ 蒙对 |
| 备份失败 | `Restoring ...` | 匹配不到 → 兜底 → **success** ❌ **假成功** |
| 备份未启动 | 文件不存在 | 直接退出，**不告警** ❌ 静默 |

> **该告警脚本在任何失败场景下都只会报"成功"，即长期处于失效状态。**
>
> 这也解释了为什么两台机器的告警状态文件长期为"无告警"。

**对比**：DB-A 的备份脚本没有 `trap`，所以它的告警**是有效的** ——
两台机器因为脚本分叉，告警一个失效、一个正常，形成了排查上的干扰。

## 3.6 阶段五：容量数学（把"偶发"变成"必然"）

**目标**：判断失败是偶然还是必然。

**做法**：把共享存储的占用、备份体积、调度节奏三者一起算。

**算账结果**：

| 指标 | 改造前 |
| --- | --- |
| 单份备份体积 | DB-A 约 460 GB，DB-B 约 180 GB |
| 稳态占用（各 2 份）| 约 1300 GB |
| 稳态占用率 | **约 68%** |
| **备份进行中的峰值** | 约 1770 GB，**约 93%** |
| 峰值时的可用余量 | **不足 10%** |

**结论**：

> 备份过程本身就要占用峰值 93% 的空间 —— **任何一次失败留下的残留，都会把余量吃穿，从而直接导致下一次失败。**
> 这不是偶发问题，是**结构性的必然**。

**失败链的自我强化机制**：

```
备份失败 → 脚本直接退出 → 【跳过末尾的过期清理】
        → 当次半成品留在存储上不删，旧备份也一份不删
        → 可用空间更少 → 下一次更容易失败 → 又留下新的残留 → …
```

## 3.7 阶段六：确认共同存储带来的故障耦合

**发现**：两台实例的备份落在**同一块 2 TB 存储**上，因此存在耦合：

- DB-B 若失败 → 不执行清理 → 占用居高不下
- DB-A 在两小时后启动时，可用空间已被挤占 → **DB-A 也会失败**

> **一台机器的故障会传染给另一台** —— 这正是"两台机器备份都出问题"这一现象的成因。

## 3.8 排查过程中使用的关键命令（只读）

| 目的 | 命令要点 |
| --- | --- |
| 查调度 | `crontab -l` |
| 查空间 | `df -hT <挂载点>` / `df -i <挂载点>` |
| 查备份清单 | `ls -lt <data目录> <log目录>` |
| 查成败历史 | `grep -n -E 'workflow started\|succeed\|failed\|Removing' <日志通配>` |
| 查失败现场 | `tail -n N <当次日志>` / `sed -n 'A,Bp' <日志>` |
| 查残留 | `ls -l /tmp/*.cnf`（临时凭证文件残留可反推"某次运行异常退出"）|
| 查进程 | `ps -eo pid,lstart,etime,rss,cmd \| grep <进程名>` |
| 校验脚本改动 | `bash -n <脚本>` / `awk` 统计 `if/fi`、`for/done` 配对 |
| 安全干跑 | `CHECK_ONLY=1 bash <脚本>`（本次新增的能力）|

**全部为只读命令，未对生产环境产生任何影响。**

# 四、问题原因

## 4.1 原因分层

| 层次 | 原因 |
| --- | --- |
| **直接原因** | 备份目标存储空间不足，`xtrabackup` 写入失败（`OS errno 28 - No space left on device`）|
| **深层原因（设计缺陷）** | 脚本采用"**先备份成功、再删旧备份**"，且**失败时直接退出、跳过清理** → **失败会留下残留并进一步压缩可用空间**，形成自我强化的失败循环 |
| **架构放大因素** | 两台实例**共用同一块存储**，容量未按"实例数 × 保留份数"规划，**故障会互相传染** |
| **监控失效** | 告警脚本靠"日志末行"判定，而备份脚本 `trap` 写入的收尾日志**覆盖了状态行** → 告警**永久性假成功** |
| **外部诱因（偶发）** | 另有一类失败由**数据库实例在备份期间异常重启**引起。此时备份数据拷贝跨越了实例重启，一致性已被破坏，备份**必然且应当失败** |
| **可观测性不足** | 备份日志仅保留 5 天，导致早期失败证据被自动清理，失败频率无法追溯 |

## 4.2 三起失败案例汇总

| 案例 | 实例 | 失败原因 | 是否告警 | 是否留下残留 |
| --- | --- | --- | --- | --- |
| 案例一 | DB-A | 未查明（证据已过保留期，仅存临时凭证文件残留）| 待核实 | 是 |
| 案例二 | DB-A | **共享存储写满**（`errno 28`）| ✅ 有告警 | 是 |
| 案例三 | DB-B | **数据库实例在备份期间重启** → 连接中断 | ❌ **无告警（监控失效）** | 是（约 180 GB 废目录）|

> 案例二的告警在当天下午被一条"已恢复"通知覆盖 —— 原因是有人**手动重跑成功**，
> 而告警脚本把"人工恢复"与"自动成功"视为同一件事，**把一次真实的失败抹掉了**。

## 4.3 一个容易被误读的细节

案例二日志中被指责的是一张约 1.3 GB 的表文件：

```
xtrabackup: Error writing file '.../db_x/tbl_y.ibd' (OS errno 28 - No space left on device)
```

**这张表本身没有任何问题** —— 它只是恰好在存储写满的那一刻被写入。
换作任何一张表，都会报出同样的错误。**排查时须避免把"最后被写入的对象"当成"故障原因"。**

# 五、解决方案

## 5.1 设计思路

针对各层原因逐一对应：

| 原因层次 | 对策 |
| --- | --- |
| 空间不足（直接）| **备份前空间预检**：不足则按规则先删旧再备份；删了仍不足则保留旧备份并告警退出 |
| 失败留残留（深层）| **失败时清理当次半成品目录**；**数据只保留 1 份**（大幅降低稳态占用）|
| 共用存储（架构）| 稳态占用由约 68% 降至约 34%，峰值由约 93% 降至约 59%，**留出足够缓冲** |
| 监控失效 | **删除 `trap` 中那行覆盖状态行的日志**，使日志末行固定为状态行 |
| 可观测性 | **日志保留期由 5 天延长至 30 天** |

## 5.2 关键设计决策

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 阈值来源 | **每次备份成功后回写实测大小**，下次直接读取 | 数据增长自动跟随，**无需人工维护**；且只认"成功"的大小，不被失败残留污染 |
| 阈值余量 | 实测值 × **120%** | 覆盖两次备份间隔内的数据增长 |
| 阈值兜底 | 状态文件缺失时**现场测量现有备份**，再退化为配置常量 | 首次运行也能正确工作 |
| 空间取值异常时 | **直接终止备份，且不做任何删除** | 存储挂载异常（如 NFS 无响应）时绝不冒险删数据 |
| "删了也不够"时 | **不删旧备份**，告警退出 | 避免白白丢失唯一一份备份却依然失败 |
| 保留份数 | **1 份**（需求），但保留天数用于日志 | 数据是空间大头，日志仅数 MB |
| 失败时 | **只删当次半成品，不动历史备份** | 失败时历史备份必须保住 |

## 5.3 改动清单

| 编号 | 改动 | 对应需求 |
| --- | --- | --- |
| **A** | 备份前空间预检 + 条件预删 | R2 / R3 / R6 |
| **B** | 备份成功后回写实测大小 | R6 |
| **C** | 数据备份只保留最近 1 份 | R1 |
| **D** | 日志保留期 5 天 → 30 天 | R7 |
| **E** | 删除 `trap` 中覆盖状态行的日志 | R4 |
| **F** | 失败时清理当次半成品目录 | R5 |

> E 仅适用于 DB-B（DB-A 无 `trap`）；F 依实施顺序先应用于 DB-B。

## 5.4 重要设计约束（后续维护必读）

> **告警脚本依靠"备份日志的最后一行"判定成败。**
> 因此：**任何新增的日志写入都必须插在状态行之前**，否则告警将再次失效。
>
> 改造后的日志末行约定：
> - 成功 → `mysql full_backup workflow completed.`
> - 失败 → `mysql full_backup failed`
>
> 本约束已写入脚本头部注释。

# 六、代码

> 以下代码已脱敏：绝对路径以变量表示，体积常量做了取整，不含任何真实标识。

## 6.1 改动 A：备份前空间预检 + 条件预删

**插入位置**：读取数据库凭证之后、创建临时凭证文件之前
（**保证预检失败退出时，不会在临时目录留下含口令的文件**）

```bash
# ===== 新增：备份前空间预检 + 条件预删 =====
# 所需空间 = 最近一次【成功】备份的实测大小 × 120%
# 该大小由脚本在每次备份成功后自动写入 $SIZE_FILE，无需人工维护
SIZE_FILE="/data/backup/run/last_backup_size"
LAST_KB=$(cat "$SIZE_FILE" 2>/dev/null)
case "$LAST_KB" in ''|*[!0-9]*) LAST_KB=0 ;; esac
if [ "$LAST_KB" -le 0 ]; then
    PREV=$(ls -1d "${BASE_PATH}/data"/*/ 2>/dev/null | grep -v "/${DAY}/$" | sort -r | head -n 1)
    [ -n "$PREV" ] && LAST_KB=$(du -sk "$PREV" 2>/dev/null | awk '{print $1}')
    case "$LAST_KB" in ''|*[!0-9]*) LAST_KB=0 ;; esac
fi
[ "$LAST_KB" -le 0 ] && LAST_KB=000000000
NEED_KB=$(( LAST_KB * 120 / 100 ))
FS_KB=$(df -Pk "$BASE_PATH" | awk 'NR==2{print $2}')
case "$FS_KB" in ''|*[!0-9]*) FS_KB=0 ;; esac
[ "$FS_KB" -gt 0 ] && [ "$(( NEED_KB * 100 / FS_KB ))" -ge 70 ] && save_log "WARN: 单份备份需 ${NEED_KB}KB，已达存储总容量 ${FS_KB}KB 的 70%，请评估扩容"
mkdir -p "$(dirname "$SIZE_FILE")"
AVAIL_KB=$(df -Pk "$BASE_PATH" | awk 'NR==2{print $4}')
case "$AVAIL_KB" in
  ''|*[!0-9]*) save_log "ERROR: 取不到 ${BASE_PATH} 的可用空间，终止备份"; save_log "mysql full_backup failed"; exit 1 ;;
esac
save_log "Space check: last_backup=${LAST_KB}KB need(120%)=${NEED_KB}KB avail=${AVAIL_KB}KB"
if [ "$AVAIL_KB" -ge "$NEED_KB" ]; then
    save_log "空间充足，按原流程执行：先备份，成功后再删旧备份"
    PRE_DELETE=0
else
    save_log "空间不足，改为先删除旧备份腾空间再备份"
    PRE_DELETE=1
fi
if [ "${CHECK_ONLY:-0}" = "1" ]; then
    save_log "CHECK_ONLY=1：仅做空间预检，未执行任何删除与备份"
    exit 0
fi
if [ "$PRE_DELETE" = "1" ]; then
    PRE_EMPTY="/tmp/empty_pre_$$"
    mkdir -p "$PRE_EMPTY"
    for T in $(ls -1d "${BASE_PATH}/data"/*/ 2>/dev/null | grep -v "/${DAY}/$"); do
        save_log "Pre-removing old backup: $T"
        rsync -a --delete "$PRE_EMPTY/" "$T" >> "$BACKUP_LOG" 2>&1 && rmdir "$T" >> "$BACKUP_LOG" 2>&1
    done
    rmdir "$PRE_EMPTY" 2>/dev/null
    AVAIL_KB=$(df -Pk "$BASE_PATH" | awk 'NR==2{print $4}')
    case "$AVAIL_KB" in
      ''|*[!0-9]*) save_log "ERROR: 删除后仍取不到可用空间，终止备份"; save_log "mysql full_backup failed"; exit 1 ;;
    esac
    save_log "已提前删除旧备份，删除后可用空间=${AVAIL_KB}KB（此刻起至新备份成功期间无可用备份）"
    if [ "$AVAIL_KB" -lt "$NEED_KB" ]; then
        save_log "ERROR: 空间仍不足(avail=${AVAIL_KB}KB < need=${NEED_KB}KB)，终止备份"
        save_log "mysql full_backup failed"
        exit 1
    fi
fi
# ===== 新增 结束 =====
```

**设计要点**：

1. **三层取值**：状态文件 → 现场测量 → 配置常量，**状态文件不存在也能正常工作**。
2. **数值合法性校验**（`case ... ''|*[!0-9]*`）：防止 `df`/`du` 异常返回空值时，算术表达式被算成 0 而误删备份。
3. **取不到空间值 → 直接退出且不删任何东西**。
4. **每条退出路径都以失败状态行收尾**，保证告警可识别。
5. **`CHECK_ONLY=1` 干跑开关**：仅做判断，不删不备份，用于上线前安全验证。

## 6.2 改动 B：成功后回写实测大小

**插入位置**：成功状态行之后

```bash
     LZ=$(du -sk "$BACKUP_DIR" 2>/dev/null | awk '{print $1}'); case "$LZ" in ''|*[!0-9]*) ;; *) echo "$LZ" > /data/backup/run/last_backup_size ;; esac
```

> 先取值再校验，`du` 失败则**什么都不写**，不会破坏状态文件。

## 6.3 改动 C：数据备份只保留最近 1 份

**改前**：

```bash
for TARGET in $(find "${BASE_PATH}/data" -maxdepth 1 -mindepth 1 -type d -mtime +5); do
```

**改后**：

```bash
for TARGET in $(ls -1d "${BASE_PATH}/data"/*/ 2>/dev/null | grep -v "/${DAY}/$"); do
```

> **只改这一行，循环体一个字都不用动** —— 新写法产出的变量同样是完整路径，后续命令照旧工作。
>
> **语义**：删除除"本次这份"以外的所有数据备份。
> 因为本次这份就是**最近一次**备份，故等价于"**只保留最近 1 份**"。
>
> **澄清一个常见误解**：这不是"只保留 1 天"—— 删除只在备份运行时发生（周一/周四），
> 所以单份备份**实际存活 3~4 天**。

## 6.4 改动 D：日志保留期延长

**改前**：`... -type d -mtime +5); do`
**改后**：`... -type d -mtime +30); do`

> 数据是空间大头，日志只有数 MB。**数据只留 1 份，日志要多留**。

## 6.5 改动 E：删除 `trap` 中覆盖状态行的日志（DB-B 专用）

**删除这一行**：

```bash
    save_log "Restoring original global timeout parameters..."
```

**保留不动**（超时参数恢复的实际动作仍然执行）：

```bash
trap '
    mysql --defaults-extra-file=$TEMP_CNF -e "SET GLOBAL ...恢复原值..." > /dev/null 2>&1
    rm -f $TEMP_CNF
' EXIT
```

> 这是"备份失败无人知晓"的**直接原因**，是本次整改中价值最高的一处改动。

## 6.6 改动 F：失败时清理当次半成品目录

**插入位置**：失败分支内、失败状态行**之前**（保证"失败"仍是日志末行）

```bash
     PART_EMPTY="/tmp/empty_part_$$"
     mkdir -p "$PART_EMPTY"
     if [ -d "$BACKUP_DIR" ]; then
         rsync -a --delete "$PART_EMPTY/" "$BACKUP_DIR/" >> "$BACKUP_LOG" 2>&1 && rmdir "$BACKUP_DIR" >> "$BACKUP_LOG" 2>&1
         save_log "Removed partial backup dir: $BACKUP_DIR"
     fi
     rmdir "$PART_EMPTY" 2>/dev/null
```

> 解决两个问题：
> ① 失败后残留占用大量空间；
> ② **该残留目录体积与正常备份几乎一致，极易被误认为"可恢复的备份"** —— 这是更危险的隐患。
>
> **只删当次残留，不动历史备份**（失败时过期清理本来就会被跳过）。

# 九、经验教训

| # | 教训 |
| --- | --- |
| 1 | **目录大小相同 ≠ 备份成功。** 备份工具在最后一步失败时，数据文件已全部拷完，产物体积与正常备份几乎一致。**判断成败只能看状态标记。** |
| 2 | **"失败时提前退出"往往跳过清理逻辑。** 清理动作写在成功分支之后，是这类脚本的常见陷阱 —— 应把清理放在**备份之前**，或确保失败路径也执行清理。 |
| 3 | **告警脚本"看日志最后一行"极其脆弱。** 任何在状态行之后追加的日志都会让它失效。应改为**全文检索最后一条状态记录**。 |
| 4 | **"已恢复"通知可能掩盖真实失败。** 人工重跑成功与自动备份成功在业务上完全不同，不应触发同一种"恢复"语义。 |
| 5 | **共享存储必须按"实例数 × 保留份数"做容量规划。** 否则故障会跨实例传染。 |
| 6 | **保留策略会销毁证据。** 日志保留期过短，会导致历史故障无法追溯 —— 数据可以少留，**日志要留久**。 |
| 7 | **不要据此判断偶发。** 把现象算成数字（峰值占用 93%）之后才发现，失败是结构性必然，不是运气问题。 |
| 8 | **改动要留底、要校验、要有干跑开关。** 本次通过"行数 + 结构配平 + 语法 + 干跑"四重校验，在运行前就排除了全部风险。 |
| 9 | **同一套脚本手工复制到多台机器会分叉。** 本次两台实例的脚本已经不一致，导致告警行为一台失效一台正常，增加了排查干扰。 |
| 10 | **先固化证据，再修改现场。** 全部排查在只读状态下完成，修改前先备份原文件并记录哈希。 |
