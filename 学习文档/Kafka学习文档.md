## 0 一页速览

| 问题 | 结论 |
|---|---|
| lag 是什么 | 尚未被消费的消息**条数**，不是时间 |
| lag 高会丢数据吗 | 不会。消息仍在 Broker 磁盘上，追平即补齐；**只有超过保留期被清理才是真丢** |
| 为什么会涨 | 生产速率 > 消费速率。要么生产突发，要么消费塌陷 |
| 表重建为什么算生产突发 | 重建 = 建新表 + 逐行 INSERT，**binlog 中每行一条 ROW 事件** |
| 积压量怎么估 | **≈ 拷表行数 ×（有触发器则 ×2）− 期间已消费量** |
| 先看哪个指标 | 生产速率与消费速率两条曲线，而非 lag 绝对值 |
| 什么情况要干预 | 单向上涨且无拐点 → 干预；已有回落趋势 → 观察 |

## 1 Kafka 是什么

**定位**：高吞吐的分布式消息中间件（也常被用作「日志流平台」），核心价值是把「数据产生」与「数据处理」解耦。

### 1.1 作用与好处

**一句话作用**：把「生产数据的一方」与「消费数据的一方」在时间和空间上分开 —— 生产者写完即走，消费者按自己的节奏读，两者互不感知、互不阻塞。

| 作用 | 机制 | 典型场景 |
|---|---|---|
| **异步解耦** | 上游写完即返回，不等待下游处理完成 | 下单后触发短信、发券、积分，不必等这些系统响应 |
| **削峰缓冲** | 瞬时高流量先落到 Kafka 磁盘，下游按自身能力匀速消费 | 大促、批量任务、上游突发写入 |
| **一对多分发** | 一份数据被多个消费组各取一份，组间互不影响 | 同一份 binlog 同时喂给数仓、搜索、缓存 |
| **可重放** | 位点可回退，按需重跑历史消息 | 下游逻辑变更后重新处理历史数据 |

**与「生产方直连下游」相比的好处：**

| 对比项 | 直连调用 | 经过 Kafka |
|---|---|---|
| 耦合度 | 上游需知道所有下游的地址与协议，新增下游要改上游 | 上游只认 topic，新增下游无需改上游 |
| 故障隔离 | 下游超时或宕机 → 上游连带超时、雪崩 | 下游宕机 → 消息先堆积，恢复后继续消费 |
| 突发流量 | 下游被瞬时流量打爆 | 先缓冲，再按能力消化 |
| 扩容方式 | 需上下游协同 | 增加消费实例即可（不超过分区数） |
| 数据回溯 | 通常无法重放 | 任意位点回退重放 |

**代价（一并要知道）**：链路变长，数据由「实时」变为「准实时」；多一层中间件，多一处运维与故障点；消息堆积、重复消费、顺序性都需要额外设计与监控。

> **适用判断**：下游多、流量有尖峰、上下游需要独立演进时值得引入；只是一次普通的同步调用，用不上它。

### 1.2 三个角色

| 角色 | 职责 |
|---|---|
| **生产者（Producer）** | 向 topic 写入消息。CDC 场景中即 binlog 抓取工具 |
| **Broker 集群** | 负责存储与副本，一组 topic 的 partition 分布在多个 Broker 上 |
| **消费者组（Consumer Group）** | 订阅并处理消息。**组内分摊、组间独立**：同组消费者分掉各分区，不同组各消费一份全量 |

### 1.3 存储模型：四条必须记住

1. **topic 是逻辑分类，物理上切成多个 partition（分区）**；单个 partition 内消息**有序、只追加**。
2. 每条消息在 partition 内有**递增编号 offset**；消费进度即消费者提交的 **committed offset**。
3. **一个 partition 在同一消费组内只能被一个消费者消费** → 消费者数超过分区数不产生额外吞吐。
4. 消息按 **retention（保留策略，按时间或按大小）** 过期删除，**删除后不可恢复**。

> 一个直观理解：topic 是快递转运中心，partition 是并行的分拣车道（各自排队、互不干扰），offset 是箱子的流水编号，消费者记着"取到第几号"。

### 1.4 关键术语

| 术语 | 释义 |
|---|---|
| **partition（分区）** | topic 的物理切分单元，也是消费并行度的上限 |
| **offset** | 分区内消息的递增编号，用来表示"处理到哪一条" |
| **binlog** | 数据库的变更流水账，每次增删改都写入一条记录 |
| **ROW 格式** | binlog 的一种记录方式：**变更多少行，就写多少条行事件** |
| **CDC** | Change Data Capture，即"抓取数据库变更并同步给下游"这件事的统称 |
| **rebalance** | 消费组内分区与消费者的重新分配，期间该组消费基本停顿 |

### 1.5 典型 CDC 链路

```
MySQL binlog → Canal（伪装成从库抓取 binlog）→ Kafka topic → 多个消费组 → 数仓 / 搜索 / 缓存 / 业务处理
```

这条链路正是 §1.1 中四个作用同时成立的典型场景：源库写完即返回、下游按各自节奏消费、同一份事件喂给多个系统、可从任意位点重放。

## 2 消费延迟是什么

### 2.1 定义

```
Lag = LogEndOffset（生产端已写到的最新位置） − CommittedOffset（消费组已提交的位置）
```

- 单位是**条数**。lag = 10 万，即 10 万条消息排队未被处理。
- 按 **group × topic × partition** 分别计算，监控看板通常按 group 汇总展示。
- 消费位点是**整组提交**的，因此某条消息卡住会顶住它所在的那个 partition。

### 2.2 四点认知纠偏

| 常见误解 | 事实 |
|---|---|
| lag 大 = 消息丢了 | 不是。消息仍在磁盘上，消费追平即补齐 |
| lag 大 = 消息多 | 不一定。也可能是**单条处理耗时过长**，条数不多但每条要好几分钟 |
| 看 lag 曲线就能定位 | 不够。必须同时看生产速率与消费速率，否则分不清哪侧异常 |
| 追平归零就没事了 | 还要看**恢复耗时**。同样是 10 万条，5 分钟追平与 5 小时追平性质不同 |

### 2.3 两类根因

延迟上涨，本质是**生产速率大于消费速率**，来源只有两种：

| 现象 | 判断 | 典型来源 |
|---|---|---|
| 生产速率出现尖峰，消费速率平稳 | **生产突发** | 批量任务、DDL、数据修复、补数 |
| 生产速率平稳，消费速率下跌 | **消费塌陷** | 发布重启、rebalance、下游慢、单条卡死 |
| 两者均正常但 lag 上涨 | 分区倾斜 | 热点 key，少数 partition 无人消费或消费过慢 |
| 消费速率周期性归零 | rebalance 抖动 | 心跳超时、单次拉取处理超时 |

## 3 案例：表重建为什么会产生十几万条积压

> 真实案例：某业务库一张约百万行、单行几 KB 至几十 KB 的日志表执行表重建，耗时约 45 分钟。期间下游 CDC 链路的消费延迟由 0 持续上涨至十几万条，重建结束后约一小时才追平。

### 3.1 前提：pt-osc 的重建本质是数据复制

常见误区是「结构未变、只是重建，不会产生数据变更」。**但在 binlog 视角下并非如此。** 在线重建工具（pt-osc / gh-ost）的实现方式是：

```
① 按原表结构创建空的新表
② 将原表数据分块 INSERT 到新表          ← 产生海量行事件
③ 在原表建触发器，把期间业务的新变更同步到新表
④ RENAME TABLE 原子换名（对外无感）
⑤ DROP 原表，空间释放
```

**关键：复制的每一行，都会在 binlog 中生成一条 ROW 事件。**

产生数据量的不是"重建"这个动作，而是**为完成重建而做的那次全量数据复制**。

| 重建方式 | 实际行为 | binlog 增量 |
|---|---|---|
| **pt-osc / gh-ost** | 建新表 + 逐行复制 + 触发器同步 + 改名 | **每复制一行 = 一条 ROW 事件，量级等同全表重写** |
| **原生 `ALTER TABLE ... FORCE`**（INPLACE 重建） | 原地重建，行内容不变 | 仅 DDL 语句事件，**基本不增长** |

**结论：问题不在"重建表"，而在"用复制工具重建表"。** 复制工具以 binlog 放大为代价，换取在线可用、不长时间锁表。

### 3.2 四条放大链路

**① 复制行事件（主体）**
`INSERT ... SELECT` 在 `binlog_format=ROW` 下展开为**每行一条 ROW 事件**。复制 10 万行即产生 10 万条事件，构成 lag 的绝对主体。

**② 触发器使量翻倍**
pt-osc 在原表上创建三个触发器（AFTER INSERT / UPDATE / DELETE），把重建期间业务的新写入 `REPLACE INTO` 到新表。这些写入**同样进入 binlog**，于是「一次业务写入」变成「两条行事件」。

**③ DDL 事件导致消费侧短暂停顿**
整个重建过程会写入 `CREATE TABLE` → `CREATE TRIGGER ×3` → `RENAME TABLE` → `DROP TABLE` → `DROP TRIGGER ×3` 等 Query 事件。CDC 工具收到 DDL 需刷新表元数据缓存，`RENAME` 后旧表名失效、临时表被 DROP，易触发重试与短暂卡顿。**生产在涨、消费在跌，lag 涨得更快。**

**④ 宽行降低单位时间吞吐**
单行几 KB 至几十 KB 的表，在"每秒多少条"相同的情况下，字节吞吐是普通表的数十倍。投递、反序列化、下游落库均更慢，**消费端本就长期处于低位**。

四项叠加的净效果：**生产侧被放大数倍，同时消费侧效率下降。**

### 3.3 量级估算

```
预计 lag 峰值 ≈ 复制行数 ×（有触发器则 ×2） − 重建期间的消费量
```

当消费端吞吐远低于复制速率时，上式退化为：

```
lag 峰值 ≈ 复制行数
```

本案例中复制十几万行、lag 峰值十几万，呈**一比一**关系 —— 说明积压几乎全部来自数据复制，业务侧并无异常增长。

> **判断口诀**：动手前先算「这次操作会在 binlog 中产生多少条行事件」。产生多少，就准备承受多少 lag。

## 4 其他容易造成积压的操作

### 4.1 生产端突发（写入量激增）

| 操作 | 机制 |
|---|---|
| **大表 DDL / 在线变更** | 本质是数据复制，逐行产生行事件（见第 3 节） |
| **批量 UPDATE / DELETE** | ROW 格式下每行一条事件；大事务还会一次性集中灌入 |
| **补数 / 数据修复脚本** | 短时间内回刷大量历史行 |
| **全表迁移 / 重建索引 / `OPTIMIZE TABLE`** | 等同于整表重写，行事件量与表行数同级 |
| **业务促销、批量下单、定时任务集中触发** | 正常写入量放大数倍，形成瞬时尖峰 |

### 4.2 消费端吞吐下降（处理变慢）

| 情况 | 表现 |
|---|---|
| **发布重启 / 实例宕机** | 消费速率归零，恢复后阶梯式爬升 |
| **rebalance 频繁触发** | 消费速率呈周期性锯齿，长期跑不满 |
| **单条消息处理卡死** | 该 partition 位点完全不推进，其余 partition 正常，易被误判为整体故障 |
| **下游慢 SQL / 接口超时** | 消费速率整体下滑，无明显报错 |
| **消费逻辑串行、批量过小** | 吞吐长期偏低，稳态下 lag 也偏高 |
| **反序列化失败 / 毒消息** | 反复重试同一条消息，形成无效循环 |
| **消费者数 > 分区数** | 多余实例空转，扩缩容无效 |
| **分区倾斜 / 热点 key** | 少数 partition lag 极高，其余正常 |

### 4.3 基础设施层

| 情况 | 影响 |
|---|---|
| Broker 磁盘接近水位 / IO 打满 | 写入被限流，消费拉取变慢 |
| 副本同步落后（ISR 收缩） | 写入阻塞，生产端抖动 |
| 网络抖动 / 跨机房链路异常 | 消费端拉取超时，反复重连 |
| 位点被重置（`auto.offset.reset=earliest`） | lag 从零重新累积至全量，等同重放 |

## 5 消费延迟过大的影响

| 影响 | 机制 | 严重度 |
|---|---|---|
| **数据时效性下降** | CDC 同步延迟，下游报表、搜索、缓存、风控读到的是旧数据 | ⭐⭐⭐ 最常见 |
| **磁盘压力** | 积压全部落在 Broker 磁盘，堆积速度快于清理速度时会撞磁盘水位 | ⭐⭐⭐ |
| **数据永久丢失** | 积压时长超过 retention → 消息被清理 → 只能下游全量重灌 | ⭐⭐⭐⭐ 最坏 |
| **消费端资源恶化** | 大批量拉取与在途消息堆积，内存与 GC 压力上升 | ⭐⭐ |
| **连锁放大** | 下游超时重试 → 重复消费 → 更慢；事务长期不提交还会持锁 | ⭐⭐⭐ |
| **分区倾斜放大** | 单分区积压打满单个消费实例，拖低整组效率 | ⭐⭐ |
| **告警疲劳** | 已知原因的告警长期占线，真实故障被淹没 | ⭐⭐ |

**判断分界线：**

- lag **有回落趋势** → 消费端仍在正常工作，观察至追平，重点盯是否反弹。
- lag **单向上涨且看不到拐点** → 必须介入，介入越晚代价越大。
