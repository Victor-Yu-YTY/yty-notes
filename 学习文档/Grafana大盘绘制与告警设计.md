# Grafana 大盘绘制与告警设计

> 本文聚焦两个主题：**大盘（Dashboard）如何绘制**、**告警（Alerting）如何设计**，以及它们各自的作用。文中涉及的服务器 IP、主机名、内部域名、账号、邮箱、看板 UID、数据源 UID 等敏感信息均已脱敏，替换为 `10.x.x.x`、`grafana.example.com` 之类的占位符；涉及业务名的实例名也已泛化。所有操作技巧都来自真实踩坑复盘，可直接对照执行。

## 〇、大盘和告警：各管什么

> **大盘解决"看得到"，告警解决"叫得应"。**

| 维度 | 大盘（Dashboard） | 告警（Alerting） |
|---|---|---|
| 本质 | 面板（查询 + 可视化）的集合 | 规则（查询 + 阈值 + 状态机 + 通知路由）的集合 |
| 面向 | 主动打开屏幕的人 | 不在屏幕前的人（企业微信/邮件/工单） |
| 关注 | 趋势、分布、当前最差、下钻细节 | 状态（Normal/Pending/Firing/NoData）、触发条件、接收人 |
| 边界 | **面板本身不配置告警**，告警是独立对象；改面板不同步改告警 | 告警表达式与面板查询是两回事，口径要人工对齐 |

操作纪律：**先查（Explore/API）→ 再改 → 改前备份 JSON → 改后验证**；写操作（`grafana_push`/`grafana_clone`）必须走审批，只读优先（`grafana_get` 用 `summary` 模式看大 JSON）。常用只读接口：`/api/dashboards/uid/{uid}`（大盘 JSON）、`/api/ruler/grafana/api/v1/rules`（告警规则）、`/api/prometheus/grafana/api/v1/alerts`（告警实例视图）、`/api/annotations?type=alert`（状态历史）；备份用 `JSON Model` 复制，跨实例导入勾 `Export for sharing externally`（不要用 Snapshot）。

## 一、大盘如何绘制

### 1.1 大盘的作用

1. **聚合**：把多数据源、多指标的信号拼成一块屏，回答"整体健康度怎么样"；
2. **定位**：靠"按最差值排序的图例表"，3 秒内说出"现在最危险的是谁"；
3. **复盘**：历史曲线回答"什么时候开始不对、持续多久"。

判断标准：**扫一眼 3 秒内能指出最危险的实例**，否则只是"图墙"。

### 1.2 绘制流程

1. **先确认数据在不在**：Explore 先跑一条肯定有数的查询；`count by (__name__) ({__name__=~"前缀.*"})` 扫指标名。"大盘没数据"十有八九是数据源/指标名不对，不是面板配错；
2. **在 Explore 调通查询**：`Empty query result`（指标/标签不存在）与 `parse error`（表达式写错）必须分清，处理方向完全不同；
3. **新建面板**：`+ Add → Visualization`，**手动确认 Data source 下拉**（默认可能继承上一个面板）；
4. **写查询、设显示**：`Code` 模式贴 PromQL/SQL，设单位/图例/阈值；
5. **布局**：24 列栅格，新面板从 `y` 最大处开始；多了用 `+ Add → Row` 分组；
6. **保存验证**：写变更说明；改前 `JSON Model` 复制备份，改坏了整份贴回。

### 1.3 三个最容易踩的查询坑

**① 数据源两级继承**：面板级 `datasource` 显示 `${Datasource}`，但查询级 `target.datasource` 钉死 uid 会**覆盖**它——切换数据源变量没反应就是这个原因。修法：JSON Model 全文替换 `"uid": "<旧uid>"` → `"uid": "${Datasource}"`，改完搜旧 uid 应为 0。

**② 时间窗口与刷新频率必须匹配**：源盘 `refresh=10s` 用 `[1m]` 合理；目标盘 `refresh=30m` 还用 `[1m]`，等于每 30 分钟只截 1 分钟样本，曲线像心电图乱跳。窗口跟着刷新走：`[5m]`/`[30m]`/`$__rate_interval`。

**③ 标签过滤**：
- IP 正则：PromQL **不支持 `\.` 转义**（直接 400），写 `"10[.]x[.]x[.]x:9100"`；
- 同一实例被多个 job 采集时**必须写 `job="..."`**，否则重复序列 → 重复曲线/告警；
- 分子分母同口径：平均耗时 = 耗时/次数，分子带实例过滤、分母没带，会算成"单机耗时 ÷ 多机总次数"，数值系统性偏小。

另外：表格面板要 `Format=Table + Instant=开`；两个查询并排成列优先用 `label_replace`，别依赖 `Join by field`（只支持单字段，多键静默失效）；聚合维度 `by (instance, ...)` 时，`on(...)`、`joinByField` 键、图例要同步改。

### 1.4 显示与变量

**显示**：该设的单位就设（percent/ms/short/bytes）；图例用 `{{instance}}`，否则多实例重名图例没法读；阈值要 `thresholdsStyle.mode` 打开才会着色，否则"没红"是假象；表格用 `organize` 重命名、用 `overrides` 做高亮（如慢查询 `COLLSCAN` 红底）；text 面板显示字面量 `$version` 通常是当前盘没建 `version` 变量。

**变量（最容易出问题）**：
- **变量只有被面板查询引用才会过滤数据**——面板查询全硬编码时，加了下拉也不起作用（"假筛选"）；
- 变量不存在时 `=~"$变量"` 被渲染成 `=~""`：**查询成功但零结果**，不报错，极易误判为"数据没采上来"；要么删 matcher、要么补建变量；
- 想"下拉显示集群名、值仍是 IP"：用 Custom 的 `显示名 : 值` 写法，并**勾上 `Skip URL sync`**（否则显示名会进 URL、旧链接残留导致全盘 No Data）；`Custom all value` 留空，别填 `.*`（会把全量实例拉进来）；
- 常量变量（`hide:2`）"碰巧能用"时要警惕：换不了、没法单独选某台，语义会被曲解。

### 1.5 复制/迁移面板

**前置三条件**（缺一个，新面板必空）：数据源存在且可选中；指标存在于目标数据源（`count(指标)`≥1）；标签格式一致（如 `instance` 必须是 `host:port`）。

**复制后必改 4 处**：数据源 uid（查询级也要看）→ 变量（`$job/$ns/...` 要么删要么补，别留成 `=~""`）→ 时间窗口 → 面板 id（冲突会静默覆盖，用 100+ 重编）。

**表格面板整段搬**：查询 A/B + `joinByField` + `organize` + `overrides` + 单位，只搬查询会得到一张乱表。跨实例（线上/线下）合并：先 `Save As` 副本 → 逐面板 `+ Add` 手工加 → 数据源用 `__inputs` 映射或 API 导入；依赖 MySQL 直连数据源的面板最后做（要 Admin 重录凭据）。

### 1.6 大盘体检与看盘

**空盘排查顺序**：数据源失效（404）→ 变量值过期 → 指标不存在 → 时间窗口/刷新不匹配。典型根因：变量 `job` 保存的值在该数据源里不存在（如保存值 `prod-mysql-xxx`、实际值 `mysql-exporter`），`job=~"$job"` 匹配不到任何序列——**顶部重选变量或选 All 即可恢复，换数据源解决不了**。

**外部导入模板盘的三层诊断**：数据源 uid 不存在（404）→ 模板依赖的指标族当前环境全无 → 目标机器根本没装采集。**Grafana 改不了采集层**，缺哪层补哪层。

**看盘三条**：① 直接看右侧图例表第一行（按最差值排序）；② 看数字别看颜色（阈值多为摆设）；③ 认口径（内存"含/不含缓存"差 10~20 个百分点，磁盘 `avail` 与 `free` 不同）。出事查看来序：压力指标（CPU/QPS/连接）→ 延迟类 → 明细表 → 存活/半同步。

### 1.7 大盘绘制坑速查

| 现象 | 根因 | 处理 |
|---|---|---|
| `Datasource not found` | 数据源 uid 失效/未改绑 | 逐面板改绑，查询级也要看 |
| 切数据源没反应 | 查询级 uid 钉死 | JSON Model 替换为 `${Datasource}` |
| 查询成功但零结果 | 变量不存在 → `=~""` | 删 matcher 或补变量 |
| 全盘空白 | 变量值过期（串环境/改名） | 重选变量或选 All |
| 曲线乱跳 | 窗口与刷新不匹配 | `$__rate_interval` |
| 阈值颜色不生效 | `thresholdsStyle.mode=off` | 打开 thresholdsStyle |
| 面板 id 冲突 | 复制未重编号 | 用 100+ 重编 |
| 表格错乱 | 只搬查询没搬转换/overrides | 整段搬 |
| "假筛选"变量点不动 | 变量未被查询引用 | 改查询引用或接受只是展示 |

## 二、告警如何设计

### 2.1 告警的作用

1. **从"人盯屏"到"屏盯人"**：夜间/周末把异常推到企业微信、邮件、工单；
2. **分级与路由**：按 severity/team 走不同渠道，让该看的人第一时间看到；
3. **状态即台账**：`Normal/Pending/Firing/NoData` 的历史就是"系统什么时候抖过"的复盘依据。

> 注意：**告警是否发出，取决于"规则评估结果 + 通知策略"，不是"有没有人看"**；读一百次告警列表也不会让告警重发。

### 2.2 从需求到规则：把"连续三次、每次三秒"翻译成参数

业务原话拆成三件事：**阈值**（超过 90%）、**评估间隔**（检查节奏）、**pending/for**（连续确认次数）。

**两个平台硬约束**：
1. Grafana 评估间隔下限 **10s**（`min_interval` 默认 10s，小于会被静默改成 10s）；
2. 数据本身没 3 秒粒度：主机 `node_exporter` 常是 15 秒采一次，3 秒评估只是重复算同一个样本，**"每次 3 秒"在数据层面没意义**。

**等价换算**：

| 方案 | 评估间隔 | pending | 最坏出告警 | 说明 |
|---|---|---|---|---|
| 推荐 | 10s | 30s | 30 秒 | 最贴近"连续 3 次、每次 10 秒" |
| 沿用现有组 | 30s | 90s | 90 秒 | 不建新组，但慢 3 倍 |

公式：Grafana 口径 **pending = 间隔 × 确认次数**；Prometheus 口径 **for = 间隔 × (次数-1)**。

**状态机时间线（10s + 30s pending）**：T0 第 1 次越界→Pending；T10、T20 继续 Pending；T30 **Firing 发通知**；中间任一次掉回阈值内→**立刻回 Normal、计时清零**。

**回话口径**（可直接用）："连续约 9 秒（3×3s）都超 90% 才告警，目的是过滤瞬时尖峰。Grafana 最小评估间隔 10 秒、数据 15 秒采一次，我按等价语义换算成 **10 秒评估 + 连续 3 次（30 秒）**，最坏 30 秒出告警。"

### 2.3 规则组与结构

```
文件夹 → 规则组（评估间隔=组级属性） → 规则（+ pending=规则级 + 标签 + 通知）
```

- **评估间隔是组级的**：想 10s 评估别动现有 30s 组，**新建组**；pending 是规则级的，可各自不同；
- 规则组在建第一条规则时顺带创建；pending 取间隔整数倍（10s/30s ✓，25s ✗）；
- 创建路径：`Alerting → Alert rules → New alert rule` → 选数据源写 PromQL（Instant）→ 加 Threshold 表达式（Input=A、Is above、勾选 Set as alert condition）→ 选/新建评估组 → 打标签 → Save；
- 规则名三段式（对象+指标+范围），名字会成为 `alertname` 的一部分——**命名即路由**。

### 2.4 表达式与阈值口径

```promql
# CPU 使用率（主机口径）
100 - (avg by (instance, nodename, object_summary) (
  irate(node_cpu_seconds_total{job="host-exporter", instance=~"10[.]x[.]x[.]x:9100", mode="idle"}[5m])
  * on(instance, job) group_left(nodename) node_uname_info) * 100)

# 内存使用率（推荐 MemAvailable 口径；老内核缺该指标时用 or 兜底 Free+Buffers+Cached，否则静默漏机器）
(1 - node_memory_MemAvailable_bytes{...} / node_memory_MemTotal_bytes{...}) * 100

# 磁盘使用率（黑名单写法，覆盖所有真实分区；排除 fuse.* 防除零得到 +Inf；/boot、/run 不纳入）
(1 - node_filesystem_avail_bytes{job="host-exporter", fstype!~"tmpfs|overlay|fuse.*|nfs.*",
        mountpoint!~"/boot.*|/run.*|/dev.*"} / node_filesystem_size_bytes{...同样过滤...}) * 100
```

**三个要点**：
- 挂载点白名单（只写 `/|/opt`）会**静默漏掉** `/data` 等分区——新机器结构不同就成盲区，优先黑名单；
- `on(instance)` 关联 `node_uname_info` 会报 `many-to-many`（多 job 采集），正确写法 `on(instance, job) group_left(nodename)`；
- 规则节点按添加顺序分字母：A=查询、C=阈值/Math；**先建 Math 占了 B 再引用 `$B` 会报 `unable to find dependent node 'B'`**。告警查询只支持 Instant。

**NoData/Error**：资源规则一般 `No Data state = OK`，采集中断用独立 `up < 1` 规则兜底（否则机器挂了不告警）；**整条查询完全无数据才触发 NoData**——13 台里某 1 台没采上会"静默不出现在告警里"，上线前必须核对采集覆盖。

### 2.5 分时段阈值：hour() 与时区陷阱（最易翻车）

真实案例：两台从库每天凌晨固定批量导致主从延迟飙升（约 1:25 达 900+ 秒），白天正常，需在凌晨窗口放宽阈值。

**三大陷阱**：
1. **`hour()` 是 UTC**：北京时间窗口先减 8 小时验算（北京 00:00–05:00 = UTC 16–20）；
2. **比较不加 `bool` 会保留原始值**：`hour() >= 16` 返回的是 hour 的值，相乘会把阈值算成 hour×阈值；
3. **`and`/`or` 是向量语义，不是布尔逻辑**：标签集合不一致时结果错乱，甚至**阈值塌陷为 0**。

一个真实坏写法（导致每天 8–9 点批量误报，实际延迟只有 1–2 秒）：
```promql
((hour() >= 0 and hour() < 2) * 7200 or (hour() < 0 or hour() >= 2) * 1200)
# 实测：北京 08:00–08:59（UTC hour=0）时结果为 0，其余时段 hour×1200 —— 告警"准点出现、准点消失"
```

**正解**（`bool` 保证恒返回 0/1 样本 + 加法分段求和）：
```promql
# 北京时间 00:00–05:00 时阈值 1200，其余时间为 3
3 + (hour() >= bool 16) * (hour() < bool 21) * 1197
```

**工程建议**：拆两条规则——普通实例全天 3 秒；特殊实例走窗口阈值。单规则内用 `instance` 标签 + `hour()` 做向量匹配极易踩坑。保存前必须核对整点边界（05:00 要回落到 3）。

> 金句：**"9 点整全部恢复"指向的是配置在整点切换，不是延迟真的恢复了。**

### 2.6 标签、路由与通知时段

- 标签（路由依据）：`severity`（分级）、`team`（**决定路由**：如 `team=DBA` → DBA 机器人）、`type`、`quality`；**新规则不打 `team` 标签就只走默认邮件**——通知"发出去了"但没人看得到；
- Contact point 留默认、靠标签走通知策略（组织内 100+ 条规则的一致做法）；
- 根路由 `group_by = [grafana_folder, alertname]` 会把同一规则的多实例**合并成一条**（磁盘 `/` 与 `/opt` 挤在一条消息）；要拆用 `Override grouping` 加 `instance`/`mountpoint`；
- `NoData` 是独立实例（`DatasourceNoData`），没有 `team` 标签 → 不走机器人路由；
- **"只在某时段通知"用 Active time intervals**（支持 Location 选 Asia/Shanghai），别用"静默取反"写法；注意 Alertmanager 告警列表**不反映** mute timing，旁路方案会出现"多发不会漏发"。

### 2.7 告警文案

- 模板：`{{ $labels.instance }}`、`{{ $labels.mountpoint }}`；数值用 `{{ printf "%.1f" $values.X.Value }}`，**X 是表达式节点 refId，写错字母消息里的数字就是空的**（真实踩过：节点是 A+C 却写 `$values.B.Value`）；
- 三个要点：Summary **带实例标识**（否则 group_by 合并后 13 条一模一样分不清）；正文带完整上下文（机器名+IP+业务别名，`nodename` 可能没用、`object_summary` 区分度不足）；把 pending 语义写进消息（"已连续 30 秒超过阈值 90%"）；
- `nodata` 时 Go 模板不渲染，会吐出 `[no value]`——下游解析要过滤无效值、回落标签兜底；
- 权威文案源是规则的 `annotations.description`，不要解析转发服务拼出的文本。

### 2.8 验证与上线

- **改规则流程**：Edit（不生效）→ 旧表达式留档 → 只改目标表达式 → `Run queries/Test rule` 验证 → Save → 查 `health=OK`、无"1s 触发"异常 → 整点边界各验一次 → 回归观察 2–3 天；
- **新建规则**：先 `Preview` 看试算值 → 保存后确认 State=Normal、组间隔正确 → **真触发验证**（阈值临时降到当前值以下，30 秒后看到 Pending→Firing；先跟接收方打招呼）→ `State history` 核对评估节奏（每 10s 一次、连续 3 次 Pending 后 Firing）；
- **上线前影响评估**：表达式预跑一遍，看哪些机器会立刻告警；核对"静默盲区"（名单里有、但 `count(指标)` 为 0 的机器）；识别坏规则（`>100` 永不触发、pending=0、采集源里没目标机器）；
- **加机器**：显式 IP 分组正则起步（`10[.]29[.]249[.](84|92|106):9100|...`），长期让 SRE 加统一标签（如 `monitor_group`）零改动；
- **上线纪律**：只读核查 → 离线断言 → 只连不发自检 → `--dry-run` 干跑（不出队）→ 真发给自己（**会出队**）→ 切正式。

### 2.9 旁路通知（案例：夜间告警汇总邮件）

需求：P0 群每晚出现"Greenplum 连接数超标"告警，要把 0–3 点的告警汇总成邮件发给负责人。

- **不能监听群消息**：企微群机器人是单向的；会话存档/回调/个人号 hook 都贵或脆。正确做法是**从告警系统侧取数**；
- **取数 API 两个反直觉**：`/api/alertmanager/grafana/api/v2/alerts` 对某些账号**恒返回 `[]`**，要用实例视图 `/api/prometheus/grafana/api/v1/alerts` 兜底；实例视图里"正在触发"的状态名是 **`alerting` 不是 `firing`**，只认一个会静默漏采；
- **降噪**：抑制窗口去重（同一告警 30–60 分钟只提醒一次）+ 汇总模式（凌晨收集、工作日 10:00 发一封，带"累计命中 N 次"）；**队列为空就不发**；跨源去重用全部标签做签名（粗键会丢掉正在触发那条）；
- **补录**：`/api/annotations?type=alert` 保留了时间+标签+当时的值，可用 `description` 模板重建"一字不差"的历史告警；
- **心跳**：每个工作日固定时间发"我还活着"邮件，否则"没告警"和"脚本挂了"分不清。

### 2.10 告警设计坑速查

| 现象 | 根因 | 处理 |
|---|---|---|
| 评估间隔 3s 不生效 | `min_interval` 默认 10s | 用 10s 档、pending 换算 |
| "准点出现、准点消失" | hour() 是 UTC / 缺 bool / and-or 语义 | `bool`+加法分段，或 Active time intervals 带时区 |
| 消息里数值是空 | `$values.X.Value` 字母错 | 核对节点 refId |
| `dependent node 'B'` 报错 | Math 先建占了 B，自引用 | 按 A 查询、C 阈值顺序建 |
| 告警进不了机器人 | 没打 `team=DBA` 标签 | 补标签，核对通知策略 |
| 多实例合并成一条消息 | `group_by` 合并 | Override grouping 加 instance/mountpoint |
| 值出现 `+Inf` | 没排除 size=0 的 fuse 文件系统 | `fstype!~"fuse.*"` |
| 机器挂了不告警 | stale 转 Normal；NoData 只认整条查询无数据 | 加 `up < 1` 规则 |
| 规则一直不触发 | 阈值 >100、采集源无机器 | 核对采集覆盖与阈值口径 |

## 四、结语

1. **先只读，再动笔**：改前 `grafana_get` 看懂现状、备份 JSON Model——大盘是共享资产，能恢复很关键；
2. **数据先于面板，面板先于告警**：空盘先查数据源/变量/指标，告警不响先查采集覆盖/阈值/组；
3. **告警要"叫得应"**：阈值、pending、标签、路由、文案、验证，缺一件就可能"存在但不工作"，上线前务必真实触发一次。
