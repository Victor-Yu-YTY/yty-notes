# MCP 速查手册

## ✍️ 我自己写的定义（原文照录）

### 定义

> 一套 ai 与外部系统通信的标准化协议

### 框架

**1、传输层**
定义 ai 和 mcp 服务端如何对话（本地：studio；远程服务：agent 通过 http 发请求；mcp 服务端通过 SSE 长连接返回结果）

**2、tools**
可供大模型调用的函数（查询服务端全部可用工具清单）

**3、resources**
喂给大模型的只读数据源链接（统一 URI）

**4、prompts**
对话模板

**5、安全控制**
1）身份凭证（只读）
2）权限控制
3）日志记录

**6、业务适配层（内部适配层）**
将 mcp 收到的标准化请求，翻译为目标业务请求体；在拿到业务返回的原始 json 数据，再包装成 mcp 协议规定的格式返回给大模型

**7、客户端配置文件**
让 ai 知道去哪连接这个 mcp 服务

### mcp 和 ai skill 的联系

> mcp 接受到 ai skill 的标准化请求；先做身份验证，权限控制，连接到目标业务；通过内部适配层翻译为目标业务请求体转发请求到后端（真实业务）；拿到后端的原始数据后，按照 mcp 协议返回结构化结果给大模型，模型依据 ai skill 的流程进行后续处理

*（原文照录。两处笔误：`studio` → `stdio`；"Skill 发请求" → 实际是宿主里的 MCP Client 发请求。下文均已修正。）*

## 0. 一句话

**MCP = AI 应用与外部工具之间的 USB-C。** 把 M×N 的集成问题降成 M+N。

⚠️ **MCP 里没有大模型。** 模型只输出"我要调哪个工具"，剩下是宿主去办。

---

## 1. 三个角色

**为什么有三个？因为「AI 应用」和「到某个服务端的连接」是两件事，要拆开。**

假设你在 VS Code 里配了两个 MCP 服务端：一个管笔记，一个连数据库。

```
┌────────────── VS Code（这就是 Host）──────────────┐
│                                                  │
│  ┌────────────────┐      ┌────────────────┐     │
│  │   Client ①     │      │   Client ②     │     │ ← VS Code 内部
│  │ 负责连笔记服务  │      │ 负责连数据库    │     │   自动创建的对象
│  └───────┬────────┘      └───────┬────────┘     │
└──────────┼───────────────────────┼──────────────┘
           │                       │
    ┌──────▼──────┐         ┌──────▼───────┐
    │ Server：笔记 │         │ Server：数据库│
    │ （一个程序） │         │ （一个程序）  │
    └─────────────┘         └──────────────┘
```

| 角色 | 通俗说 | 具体是什么 |
|---|---|---|
| **Host** | 你用的那个 AI 软件 | **VS Code 本身**。它负责调模型、管对话、显示界面 |
| **Client** | Host 里"负责连某一个服务端"的那根线 | **不是一个独立程序**，是 VS Code 代码里的一个对象。连 2 个服务端就有 2 个 |
| **Server** | 真正提供工具的那个程序 | **就是个普通程序**。本地跑（子进程）或远端跑都行 |

**三个最容易搞错的点：**

1. **Client 不是程序** —— 它是宿主内部的一个对象。你看不见它，也不用单独启动它。
2. **Server 就是普通程序** —— "读文件的 Server"，说白了就是一段能读文件的代码，没有神秘东西。
3. **大模型不是这三个角色之一** —— 它完全不参与 MCP。只是宿主把工具清单念给它听，它说"我要调这个"。

> **记忆钩子：Host 是总机，Client 是它拨出去的每一条线，Server 是接线的那一头。**

## 2. 框架七条

### ① 传输层

| 传输 | 用在哪 | 机制 |
|---|---|---|
| **stdio** | **本地，最常用** | 子进程的 stdin/stdout，没有 HTTP |
| **Streamable HTTP** | 远程 | 客户端 **POST** 发请求，**可选** SSE 回传 |
| ~~HTTP+SSE~~ | 已废弃 | 不要用 |

⚠️ **stdout 是协议通道，日志一律走 stderr。**

### ② tools（工具）

可执行的函数，**模型决定调用**，**有副作用**。
`tools/list` 查清单 → `tools/call` 调用。

### ③ resources（资源）

**只读**数据，用 **URI** 标识（`notes://all`）。
**由应用/用户决定何时读**，模型不能自己伸手拿。

### ④ prompts（提示词模板）

**可复用的对话模板，用户主动触发**（如斜杠命令）。

> ⭐ **三种原语的区别 = 控制权归谁**
> 工具归**模型** / 资源归**应用** / 提示词归**用户**

### ⑤ 安全控制

| 项 | 要点 |
|---|---|
| **身份凭证** | OAuth / Token。最小权限，绝不写进仓库 |
| **权限控制** ⭐ | **没权限的工具，AI 连它存在都不知道**（不是调用了才拒绝） |
| **只读标注** | 每个工具声明会不会改数据，宿主据此决定弹不弹审批框 |
| **日志记录** | 走 stderr；记录调用方身份和筛选过程 |

**权限裁剪顺序**：黑名单 → 白名单 → 只读 → 权限

**三个攻击面**：工具投毒（description 藏指令）、提示词注入（返回数据藏指令）、混淆代理。

### ⑥ 业务适配层

```
MCP 请求 → 翻译成业务请求体 → 拿原始 JSON → 精简 → 包成 MCP 格式返回
```

**占代码量绝大部分，但跟 MCP 协议本身无关**（是外面那个业务系统复杂）。

### ⑦ 客户端配置文件

**宿主侧**的配置，告诉宿主去哪连。分两种：

```jsonc
// 本地 stdio
{ "mcpServers": { "x": { "command": "node", "args": ["server.ts"] } } }

// 远程 HTTP
{ "mcpServers": { "x": { "type": "http", "url": "https://...", "headers": {...} } } }
```

密钥用 `${input:xxx}` + `password: true` 弹框输入，**不写死在文件里**。

## 3. 消息格式（外壳就四种）

```jsonc
// 1. 请求（有 id，要回包）
{ "jsonrpc": "2.0", "id": 1, "method": "tools/list", "params": {} }

// 2. 成功响应
{ "jsonrpc": "2.0", "id": 1, "result": { ... } }

// 3. 错误响应
{ "jsonrpc": "2.0", "id": 1, "error": { "code": -32602, "message": "..." } }

// 4. 通知（没有 id，不回包）
{ "jsonrpc": "2.0", "method": "notifications/tools/list_changed" }
```

### 方法名速查

| 干什么 | 方法名 |
|---|---|
| 列工具 / 调工具 | `tools/list` / `tools/call` |
| 列资源 / 读资源 / 列模板 | `resources/list` / `resources/read` / `resources/templates/list` |
| 列提示词 / 取提示词 | `prompts/list` / `prompts/get` |

### 调用工具的真实样子

```jsonc
// 请求
{ "method": "tools/call",
  "params": { "name": "add_note", "arguments": { "text": "内容" } } }

// 成功
{ "result": { "content": [ { "type": "text", "text": "已保存" } ] } }

// 失败（⚠️ 走 result，不是 error）
{ "result": { "content": [ { "type": "text", "text": "笔记不存在，请先 list_notes" } ],
              "isError": true } }
```

## 4. 一个工具的 8 个要素

| # | 要素 | 关键点 |
|---|---|---|
| 1 | 分组 | 便于分组开关 |
| 2 | **名字** | 模型调用时用它 |
| 3 | **说明** ⭐ | **写给 AI 看的**：做什么 + 什么时候用 + 什么时候别用 |
| 4 | **只读标注** ⭐ | `readOnlyHint` / `destructiveHint`，默认要保守 |
| 5 | **参数表** | JSON Schema，从类型自动生成 |
| 6 | **权限要求** | 调用我需要什么权限 |
| 7 | 参数校验 | 执行前挡掉非法输入 |
| 8 | 执行逻辑 | 真正干活 |

## 5. 八个坑

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | 用 `console.log` 打日志 | ⚠️ stdout 是协议通道，日志走 stderr |
| 2 | 说明写得太随意 | 说明是**写给 AI 看的** |
| 3 | 参数错误当协议错误抛 | 返回 `isError` 的**正常结果**，模型才能自纠 |
| 4 | "查不到"标成错误 | **查不到 ≠ 出错**，标了模型会反复重试 |
| 5 | 默认把工具标成"安全" | 默认保守，**写操作显式声明** |
| 6 | 工具名随意改 | 会搞崩已接入的用户 |
| 7 | 返回一大堆无用字段 | 上下文要花钱，只返回有用的 |
| 8 | URI 变量直接拼文件路径 | 必须校验是否越出根目录 |

## 6. Skill 与 MCP

| | **Skill** | **MCP** |
|---|---|---|
| 本质 | **操作手册**（Markdown 文本） | **工具箱**（程序） |
| 回答 | "这件事该怎么做" | "我有哪些能力可用" |
| 类比 | **菜谱** | **厨房设备** |

**Skill 不会发任何请求。** 它被加载进模型上下文，让模型知道该按什么流程调哪些工具。
**真正发请求的是宿主里的 MCP Client。**

```
Skill（文本）→ 进模型上下文 → 模型决定调哪个工具 → 宿主发请求
  → MCP 服务端（验身份、查权限）→ 业务适配层 → 真实后端
  → 精简包装 → 返回宿主 → 喂给模型 → 模型按 Skill 流程继续
```

⭐ **两者唯一的接口 = 工具名。** 名字对不上就是 `Tool not found`。

> **你的 MCP 不需要知道 Skill 的存在，也不需要为它做任何特殊处理。**

## 7. 只记这三句

> **1. MCP 是 AI 工具的 USB-C** —— M×N 降成 M+N。
>
> **2. 三种原语的区别是"控制权归谁"** —— 工具归模型，资源归应用，提示词归用户。
>
> **3. 一份完整实现，一半内容是在管住 AI 的权限** —— 没权限的工具，AI 连它存在都不该知道。
