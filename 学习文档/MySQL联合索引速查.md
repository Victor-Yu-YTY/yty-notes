# MySQL 联合索引速查

> 速查向文档：每节只留结论与判据。适用 MySQL 8.0 + InnoDB。表名已脱敏为通用示例。

---

## 0 一页决策卡

| 你的情况 | 该怎么做 |
|---|---|
| WHERE 有多个**等值**条件 | 全部放进同一条联合索引（一条顶多个单列索引） |
| 有**等值 + 范围** | 等值列在前，范围列在后 |
| 想消掉 `ORDER BY` 排序 | `ORDER BY` 列紧跟等值列之后，方向一致 |
| 查询**缺最左字段** | 见第 4 节六种解法 |
| 加了索引还是全表扫 | 查 `EXPLAIN` 的 `key` 是否为 `NULL`，再对照第 5 节 |
| 前导列命中率 > 30% | 换高选择性列做前导（否则索引白建） |

## 1 什么是联合索引

**联合索引（复合索引 / 组合索引）= 把两列及以上的值放在一起排序建成的一棵索引树。**

```sql
-- 单列索引：各自独立的两棵树
ADD INDEX idx_a (a);
ADD INDEX idx_b (b);

-- 联合索引：一棵树，先按 a 排，a 相同再按 b 排
ADD INDEX idx_a_b (a, b);
```

| 对比 | 多个单列索引 | 一条联合索引 |
|---|---|---|
| 多条件查询 | 依赖 index merge，**不保证生效** | 一次定位，稳定生效 |
| 能否免排序 | 不能 | 能（`ORDER BY` 与索引顺序对齐时） |
| 能否覆盖 | 单列覆盖范围小 | 多列都可覆盖 |
| 空间 | 各自一棵树 | 一棵树，通常更省 |

> 结论：**多条件查询优先建一条联合索引，而不是堆多个单列索引。**

---

## 2 为什么快：三个能力

索引的本质是「**排好序 + B+ 树**」。有序带来三种能力：

| 能力 | 作用 | 谁在受益 |
|---|---|---|
| **定位** | 从千万行里直接跳到目标段 | WHERE 等值 / 范围 / IN |
| **免排序** | 天然按索引顺序返回 | ORDER BY / GROUP BY / DISTINCT |
| **覆盖** | 需要的列都在索引里，不回表 | SELECT 列全在索引内 |

**联合索引的排序结构**（索引 `(a,b,c)`）：

```
a=1  b=1  c=1
a=1  b=2  c=1      ← a 是第一排序键
a=2  b=1  c=1      ← b 只在 a 相同的段内有序
a=2  b=2  c=1
```

这就是后面"最左前缀"的物理根因：**次级列只在上级列相同的范围内有序**。

**回表成本**：二级索引叶子存 `(索引列值, 主键值)`，定位后还要回主键树取整行 = 一次随机 IO。
**覆盖索引**（需要的列都在索引里）可免回表，`EXPLAIN` 显示 `Using index`。

## 3 怎么创建

```sql
-- 基础语法
ALTER TABLE db_name.t_name
  ADD INDEX idx_a_b_c (a, b, c);

-- 生产环境用在线 DDL（不阻塞读写）
ALTER TABLE db_name.t_name
  ADD INDEX idx_a_b_c (a, b, c),
  ALGORITHM=INPLACE, LOCK=NONE;
```

**实操要点**

| 项 | 建议 |
|---|---|
| 命名 | `idx_<列1>_<列2>`，或 `idx_<业务>_<列>`，与既有命名风格统一 |
| 一次加多条 | 合并到同一条 `ALTER`，只扫一次表：`ADD INDEX i1 (...), ADD INDEX i2 (...)` |
| 前置参数 | `SET GLOBAL innodb_online_alter_log_max_size = 1073741824;`（默认 128M 容易被写入撑爆导致回滚）|
| 锁等待 | 执行前 `SET SESSION lock_wait_timeout = 30;`，拿不到 MDL 锁快速失败而不是卡住业务 |
| 粒度 | 每次只跑一条表，串行执行，避开业务高峰与夜间批处理 |
| 降序索引 | 需要 `ORDER BY a DESC, b ASC` 时用 `ADD INDEX idx (a DESC, b ASC)` |

## 4 最左前缀法则

**规则**：索引 `(a,b,c)` 只有在条件里出现 `a`（或 `a,b`、`a,b,c`）时，才能被用于**定位**。

**判定形式不限**：`=`、`IN`、`BETWEEN`、`>`、`IS NULL` 都算"用到了这一列"。

以索引 `(a,b,c)` 为例：

| WHERE 条件 | 能否定位 | 说明 |
|---|---|---|
| `a=?` | ✅ | 用到 a |
| `a=? AND b=?` | ✅ | 用到 a、b |
| `a=? AND b=? AND c=?` | ✅ | 三列全用 |
| `a=? AND c=?` | ⚠️ 部分 | 只能用 a 定位，c 无法定位 |
| `a>?` | ✅ | 用到 a（范围） |
| `a=? AND b>?` | ✅ | a 定位 + b 范围 |
| `a=? AND b>? AND c=?` | ⚠️ 部分 | c 在范围之后，**只能过滤不能定位** |
| `b=?`；`c=?`；`b=? AND c=?` | ❌ | 缺最左列 → 见下节 |

> 记忆法：**电话簿按「姓+名」排序，你只知道"名"就翻不到那一页。**

## 5 触发条件：不止 WHERE

**索引有两种能力**：WHERE 用「定位」，ORDER BY / GROUP BY 用「有序」。只盯 WHERE 会漏掉一半优化空间。

| 语句成分 | 能否用索引 | 靠哪种能力 |
|---|---|---|
| WHERE 等值 / IN | ✅ | 定位（最有效） |
| WHERE 范围 | ✅（命中率低才划算） | 定位 |
| **ORDER BY** | ✅ | 有序 → 免 `Using filesort` |
| **GROUP BY** | ✅ | 有序 → 免 `Using temporary` |
| DISTINCT | ✅ | 有序 |
| **JOIN 关联列** | ✅ | 定位（JOIN 优化核心） |
| MIN / MAX | ✅ | 有序（直接取端点，接近 O(1)） |
| LIMIT | ✅ | 有序（可提前终止） |
| SELECT 列 | ✅ | 覆盖 → 免回表 |
| HAVING | ❌ | 聚合之后才过滤 |

### 5.1 ORDER BY 免排序的四个条件

排序列是索引前缀或紧跟等值列之后；方向一致；列上无函数运算；没被 `OR` 打断。

| 查询（索引 `(a,b,c)`） | 免排序 | 原因 |
|---|---|---|
| `WHERE a=? ORDER BY b` | ✅ | b 紧跟等值列 |
| `WHERE a=? ORDER BY b,c` | ✅ | 连续前缀 |
| `WHERE a=? ORDER BY c` | ❌ | 跳过 b |
| `ORDER BY b` | ❌ | a 不在条件里，索引整体按 (a,b) 有序 |
| `WHERE a IN (1,2) ORDER BY b` | ⚠️ 常仍 filesort | 多个 a 值的 b 需归并 |
| `WHERE a>? ORDER BY b` | ❌ | a 是范围，之后无法定位/排序 |

### 5.2 JOIN

- 驱动表（`EXPLAIN` 第一行）可以没索引，它只扫一次
- **被驱动表（第二行）的关联列必须有索引**，否则驱动表每行触发一次全扫
- 两表关联列**字符集 / collation 不一致** → 索引直接失效

### 5.3 一个反直觉点

WHERE 用不上索引时，`ORDER BY + LIMIT` 也可能走索引；但若 WHERE 筛不掉多少行，会变成"扫全索引 + 逐行判断"，**可能比全表扫更慢**。

> 判断依据永远是 `EXPLAIN` 的 `rows`（预计扫描行数），不是"有没有用上索引"。

## 6 用不上最左字段怎么办

场景：索引 `(a,b,c)`，查询只有 `WHERE b=? AND c=?`。

| 方案 | 做法 | 成本 | 前提 / 风险 |
|---|---|---|---|
| **1 调整索引顺序** | 改建成 `(b,c,a)` | 空间 0 | 需评估原 `WHERE a=?` 的查询；**首选** |
| **2 新建以该列开头的索引** | `ADD INDEX (b,c)` | 中 | 仅长期高频时值得；若 `(b,c)` 是 `(b,c,a)` 的前缀，只建长的那个 |
| **3 给 SQL 补最左列** | `WHERE a IN (1,2,3) AND b=?` | 0 | 最左列可枚举且值少；**语义必须等价**；定时任务改造最常用 |
| **4 Index Skip Scan** | 8.0.13+ 优化器自动改写 | 0 | 最左列基数极低才有效；**不保证生效**；不能用于排序 |
| **5 手工 UNION ALL** | 按 a 的取值分别查再合并 | 0 | 取值固定且少；`UNION` 会多一次去重排序 |
| **6 覆盖索引兜底** | 把 SELECT 列全放进索引 | 大 | 索引变宽，写入成本长期上升 |

**选型顺序**：先 3（改 SQL 最便宜）→ 再 1（顺序可能只是历史遗留）→ 再 2 → 最后 4/5/6。

**验证 skip scan 是否生效**：`EXPLAIN` 的 `Extra` 出现 `Using index for skip scan`。

## 7 失效案例

| # | 情形 | 问题 | 正确做法 |
|---|---|---|---|
| 1 | 跳过最左列 `WHERE b=?` | 无法定位 | 见第 6 节 |
| 2 | 列上运算 `WHERE DATE(t)=?` | 运算后无法用索引定位 | 改范围 `t>=? AND t<?` |
| 3 | 列上函数 `WHERE UPPER(n)=?` | 同上 | 函数索引（8.0.13+）或改写条件 |
| 4 | 隐式类型转换 `WHERE varchar_col=123` | 字符串被转数字 | 参数类型与列类型一致 |
| 5 | `LIKE '%abc'` 前置通配 | 无法确定起始前缀 | 改后缀匹配或全文索引 |
| 6 | `OR` 连接不同列 `A=? OR D=?` | 涉及不同索引，可能退化为全扫 | 拆 `UNION ALL`，或建 `(A,D)` |
| 7 | `!=` / `NOT IN` / `NOT LIKE` | 取反通常命中大部分数据 | 改正向条件 + 排除表 |
| 8 | **范围列之后的列** `A=? AND B>? AND C=?` | C 只能 ICP 过滤，无法定位 | 把 C 放到 B 前面：`(A,C,B)` |
| 9 | **前导列命中率 > 30%** | 优化器判定全表扫更便宜 | 换高选择性列做前导 |
| 10 | JOIN 字符集 / collation 不一致 | 关联列无法比较 | 统一字符集与排序规则 |
| 11 | 统计信息过期 | 优化器成本估算失准 | `ANALYZE TABLE` |
| 12 | 查询列多、回表成本高 | 优化器认为全扫更优 | 做覆盖索引或拆查询 |
| 13 | `IS NOT NULL` 命中大比例 | 等于扫大部分数据 | 视分布，必要时加冗余标记列 |
| 14 | 排序方向冲突 `ORDER BY A DESC, B ASC` | 与索引顺序不同向 | 建降序索引 |

> **注意 9**：这类失效最隐蔽 —— `EXPLAIN` 会显示 `possible_keys` 有值但 `key=NULL`，即"优化器看到了索引，主动放弃"。

## 8 字段顺序怎么定

### 8.1 决策流程

```
① 全部等值 / IN 列 —— 能定位，放最前
② 范围条件列 —— 只能筛选，放其后
③ ORDER BY 列 —— 与范围列相同可顺带免排序
④ 必要时补列做覆盖索引（慎用宽列）
```

### 8.2 等值列之间怎么排

| 依据 | 说明 |
|---|---|
| 区分度从高到低 | 优先让高区分度列先定位 |
| 低频查询的条件靠后 | 让索引能被更多查询复用 |
| 事实上顺序影响有限 | 只要等值列都在同一索引内，InnoDB 都能定位；顺序主要影响索引体积与 ICP 效率 |

### 8.3 选择性临界值（判断能否做前导列）

| 条件命中率 | 效果 |
|---|---|
| < 5% | 极佳 |
| 5% ~ 20% | 良好 |
| 20% ~ 30% | 边缘，可能被放弃 |
| **> 30%** | **大概率全表扫，索引白建** |

### 8.4 成本与数量

| 项 | 量级 |
|---|---|
| 空间 | datetime 单列 ≈ 17~18 字节/行；1000 万行约 170 MB |
| 写入 | 每多一个索引，INSERT/UPDATE 多一次维护 |
| 数量 | 单表二级索引建议 ≤ 5~8 个，超过做冗余审计 |

**冗余判定**：`(A)` 是 `(A,B)` 的最左前缀 → `(A)` 冗余可删。

```sql
SELECT TABLE_NAME, INDEX_NAME, GROUP_CONCAT(COLUMN_NAME ORDER BY SEQ_IN_INDEX) AS cols
FROM information_schema.STATISTICS WHERE TABLE_SCHEMA='your_db'
GROUP BY TABLE_NAME, INDEX_NAME;
```

## 9 建完怎么验

```sql
-- ① 计划是否改变：从 ALL/index 变成 range/ref，filesort 消失，rows 大幅下降
EXPLAIN SELECT ... ;

-- ② 索引是否真被使用（建好 3~5 分钟后查，必须 > 0）
SELECT INDEX_NAME, COUNT_STAR AS 使用次数
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE OBJECT_SCHEMA='your_db' AND OBJECT_NAME='your_table';

-- ③ 真实耗时：间隔 5~10 分钟采两次算差值（累计平均值会被历史慢执行拉高）
SELECT COUNT_STAR, SUM_TIMER_WAIT, SUM_ROWS_EXAMINED
FROM performance_schema.events_statements_summary_by_digest
WHERE DIGEST_TEXT LIKE '%your_table%';
```

**三条判据**：`key` 不为 `NULL` + `使用次数 > 0` + `扫描行数` 下降。三者缺一，说明索引没起作用。
