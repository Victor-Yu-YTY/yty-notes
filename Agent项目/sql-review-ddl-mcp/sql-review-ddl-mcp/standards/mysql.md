# MySQL使用规范

> **本文件是通用总纲（人读 + 可追溯），不参与机器判定。**
> 机器执行口径以 `standards/ddl.md`（DDL）与 `standards/dml.md`（DML）为准；
> 每条条款在文末《条款与规则对照表》里标注了它落到哪条规则、或为什么不在本服务审核范围。
> 改总纲不影响服务结论；要让服务按新口径判定，改 `ddl.md` / `dml.md`（见 `standards/README.md`）。

## **建库**

* **【强制】**命名规范："demo_" + 业务描述简写，总长度不超过64
* **【强制】**库名小写，禁止使用MySQL保留字

            *例外：如有第三方数据库建库需求，不支持自定义库名，则可不按此规范定义*

## **建表**

* **【强制】** 表名、字段名使用**大写字母**，'_' 下划线分割，表名最前面加上业务名
* **【强制】** 表名、字段名禁止使用 MySQL 保留字
* **【强制】** 表及字段必须有注释，修改字段含义和更新状态值时，及时更新注释
* **【强制】** 禁止修改 字段名，应创建新字段，确认无业务使用后再删除
* **【强制】** 存储浮点数必须使用 DECIMAL，禁止使用 FLOAT 和 DOUBLE
* **【强制】** 禁止使用 ENUM，SET 类型，使用 TINYINT 来代替
* **【强制】** 禁止在数据库中使用 VARBINARY、BLOB 存储图片、文件，使用文件服务器存储
* **【强制】** 时间字段统一使用 DATETIME，不允许为"0000-00-00 00:00:00" 或者 "0000-00-00" 值，~~无效默认值推荐为 "1970-01-01 00:00:00"~~ 改为"2000-01-01 00:00:00"
* **【强制】** 所有字段都定义为 NOT NULL，默认值也不应该为 NULL
* **【强制】** 禁止修改字符集、字段名、索引名，禁止修改字段顺序，禁止删除字段
* **【强制】** 每张表必须包含的字段： ID、CREATE_TIME、MODIFY_TIME、IS_DEL、__MODIFY_TIME__

  ```sql
  ID bigint NOT NULL AUTO_INCREMENT COMMENT '无意义主键ID',
  IS_DEL tinyint NOT NULL DEFAULT 0 COMMENT '是否删除',
  CREATE_TIME datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  MODIFY_TIME datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '修改时间',
  __MODIFY_TIME__ datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT 'BI'
  ```
* **【强制】不要在业务中去使用历史表、归档表、临时表、备份表**
* **【强制】历史表名** 必须以 *'_HISTORY'* 为后缀
* **【强制】归档表名** 必须以 *'ARCHIVER_'* 为前缀
* **【强制】临时表名** 必须以 *'_TMP_创建日期_保留月份'* 为后缀，到保留月份后删除
  * 如：DEMO_CITY_TMP_20190912_3，临时表于 2019年9月12号创建，**3个月后可删除**
* **【强制】备份表名** 必须以 *'_BAK_创建日期_保留月份'* 为后缀，到保留月份后，**默认迁移至归档库中，并从原库删除**
  * 如：DEMO_CITY_BAK_20190912_3，备份表于 2019年9月12号创建，原库保留三个月

 

* **【推荐】** 建表时需显示指定 InnoDB 存储引擎，字符集统一使用 utf8mb4
* **【推荐】** 名称应见名知意，建议使用名词而不是动词
* **【推荐】** 单表字段数控制在 30 以内
* **【推荐】** 单库表数量控制在 500 以内
* **【推荐】** 基于够用就行的原则，尽量使用较小和准确的数据类型

  
  1. 使用 UNSIGNED 存储非负数值
  2. 建议使用 INT UNSIGNED 存储 IPV4
  3. 整型定义中不添加长度，比如使用 INT，而不是INT(4)
  4. 使用短数据类型，比如取值范围为 0-100 时，使用 TINYINT UNSIGNED
  5. VARCHAR(N)，N 表示的是字符数不是字节数，比如 VARCHAR(255)，最大可存储255个汉字，需要根据实际的宽度来选择 N
  6. VARCHAR(N)，N 尽可能小，因为 MySQL 一个表中所有的 VARCHAR 字段最大长度是 65535 个字节，进行排序和创建临时表一类的内存操作时，会使用N的长度申请内存
  7. 存储日期使用 DATE 类型
  8. 如果定义的 CHAR 字段超过 CHAR(20)，则改为 VARCHAR 类型
* **【推荐】** 单表行数超过 2000 万行或者单表容量超过 20GB，推荐进行分库分表， 如果预计三年后的数据量达不到这个级别，无需在创建表时就分库分表
* **【推荐】** 字段尽量不用text类型，如特殊情况，可新建子表，单独存放text字段，与主表通过主键关联
* **【推荐】** 索引不建议删除，如果有需求，审批严格执行，且责任划分清楚

\n

* **【参考】** 字段允许适当冗余，以提高查询性能，但必须考虑数据一致。冗余字段应遵循：
  * 不是频繁修改的字段，如：用户姓名
  * 不是 VARCHAR 等超长字段，更不能是 text 字段
* **【参考】** .

 

## **建索引**

* **【强制】** 非唯一索引必须按照 ***"IDX_字段名称\[_字段名\]"*** 进行命名，如组合索引字段比较多，字段名称可缩写，减少索引名称长度
* **【强制】** 唯一索引必须按照 ***"UNIQ_字段名称\[_字段名\]"*** 进行命名，如组合索引字段比较多，字段名称可缩写，减少索引名称长度
* **【强制】** 索引名称必须使用大写
* **【强制】** 对长度过长的 VARCHAR 字段建立索引时，必须添加前缀索引，前缀索引不应该超过8个字符
* **【强制】** 禁止使用外键，应放到程序端实现
* **【强制】** 禁止大文本字段出现在普通索引、唯一索引、组合索引中
* **【强制】**每张表必须包含以下三个索引：

  ```sql
  PRIMARY KEY (ID),
  KEY IDX_CREATE_TIME (CREATE_TIME),
  KEY IDX__MODIFY_TIME__ (__MODIFY_TIME__)
  ```

 

* **【推荐】** 索引中的字段数建议不超过5个，且尽量不使用大字段进行索引
* **【推荐】** 单张表的索引数量控制在5个以内，根据表字段个数动态调整
* **【推荐】** 能使用唯一索引就使用唯一索引，唯一索引字段数控制在 3个以下
* **【推荐】** 索引字段的顺序需要考虑字段值去重之后的个数，个数多的放在前面，等值条件列放在前面
* **【推荐】** ORDER BY、GROUP BY、DISTINCT 需要用在索引字段上
* **【推荐】** 合理创建联合索引，避免冗余，(a,b,c) 相当于 (a) 、(a,b) 、(a,b,c)

 

* **【参考】**创建索引时避免有如下极端误解
  * 宁滥勿缺： 认为一个查询就需要建一个索引
  * 宁缺勿滥： 认为索引会消耗空间、严重拖慢更新和新增速度
  * 抵制唯一索引： 认为业务的唯性一律需要在应用层通过"先查后插"方式解决
* **【参考】** 创建索引尽量满足三星索引条件，三星条件如下：


* * 索引的区分度很高
  * 索引的排序和业务查询的排序相同
  * 索引的字段完全满足查询的需要
* **【参考】** 尽量遵循ESRO规则：
  * E:首先添加等值字段
  * S:其次添加排序字段
  * R:再次添加范围查询字段
  * O:最后添加select语句的其它字段 如select 处的，join处的 where 条件没有用剩下的字段

例：\nselect t2.c1,t2.c3,t2.c6,t2.c50,t3.xx from t2 left join t3 on t2.c40 = c3.c1 where t2.c1=xx and t2.c30 = xx and t2.c2 != xx and t2.c6 between 10 and 100 order by t2.c8\n依据ESRO原则\n（1）、我们需要先添加C1与C30 等值查询字段，我们再根据三星索引原则判断一下C1与C30的区分度，发现C1区分度很低。为性别字段，所以我们就可以先只加C30字段 idx(c30,\n（2）、然后添加 排序字段 idx(c30,c8,\n（3）、然后添加范围字段 同样去判断一下c6的区分度。如果还行则添加 idx(c30,c8,c6,\n（4）、然后添加where 处的其它字段 idx(c30,c8,c6,c1,c2 添加c1,c2 不仅了为了索引覆盖，也可以实理ICP(索引下推)\n（5）、添加剩余的其它字段 select字段和join字段 idx(c30,c8,c6,c1,c2,c3,c40) c50为主键，二级索引叶子节点有，所以不需要添加。

## **SQL语句执行规范**

* **【强制】** 禁止物理删除数据，所有数据必须是逻辑删除，除了数据归档、迁移
* **【强制】** UPDATE、DELETE 语句禁止使用 LIMIT、ORDER BY
* **【强制】** UPDATE、DELETE 必须添加 WHERE 条件，并且使用索引
* **【强制】** WHERE 条件中必须使用相同的类型，避免隐式类型转化
* **【强制】** 禁止在 SELECT 语句中出现 *SELECT \* FROM*
* **【强制】** INSERT 语句必须显式的指明字段名称，禁止使用 INSERT INTO TABLE_NAME ()，而应该使用 INSERT INTO TABLE_NAME (F1, F2, F3) VALUES ('1','2','3')
* **【强制】** 避免在 WHERE 条件左侧进行 数学或者函数运算，会导致索引失效
* **【强制】** 禁止使用 存储过程、触发器、函数，应通过程序逻辑实现
* **【强制】** 禁止单条 SQL 语句同时更新多个表
* **【强制】** 禁止使用 FORCE INDEX 在 SQL 中强制指定索引名称
* **【强制】** 不要使用 COUNT(列名) 或 COUNT(常量) 来替代 COUNT(\*)，MySQL 会对 COUNT(\*) 进行优化
* **【强制】** 不允许使用 create table xx select 语法 如有初始化数据需求 请分成两步走
* **【强制】** 禁止使用 % 前缀模糊查询，例如 LIKE "%XXX"，这将导致全表扫描，只支持左前缀匹配
* **【强制】** 除清洗数据外，不允许业务使用 REPLACE INTO 逻辑
* **【强制】** ALTER 操作时（如加字段、修改字段、加索引等），如果对同一张表的多个操作，应合并到一条语句中一起执行\n


* **【推荐】** SQL语句中IN包含的值不应过多（单批次不超过200）
* **【推荐】** WHERE条件中的非等值条件（IN、BETWEEN、<、<=、>、>=）会导致后面的条件使用不了索引，使用时要谨慎
* **【推荐】** INSERT 语句使用 批量提交，如 *INSERT INTO TABLE_NAME (F1, F2, F3)  VALUES (),(),()* ，VALUES 的个数不应过多
* **【推荐】** 不使用 ORDER BY RAND() 使用其他方法替换
* **【推荐】** 尽量避免使用子查询
* **【推荐】** 避免大事务，事务要尽量小，能在两个事务里处理的不要合并成一个事务处理，大事务降低并发能力，且容易引发死锁
* **【推荐】** 如有生产数据查询需求，可通过SQL审核平台查询
* **【推荐】** 如有SQL导出需求，数据通过企业微信单独给，不管是否有敏感数据（回复邮件的话，接收人较多，容易数据泄露） 
* **【推荐】** 使用 UI 工具（如：Navicat）操作时，所有操作通过 SQL 执行，避免使用图形化页面，减少误操作的可能
* **【推荐】** update / delete 根据需求做备份


* * 少量数据备份，可以原库中创建备份表，也可以导出文件存储本地


* * 大量或重要业务数据按照需求，使用mysqldump备份成 sql文件，归档服务器中存储 

## **工单规范**

* **【强制】** 日常数据查询、数据修正（影响行数较少的场景）通过SQL审核平台（[sql-review.example.com](https://sql-review.example.com/#/login)）申请执行
* **【强制】** 上线单中的SQL（影响行数较多）、或风险较高的数据库操作，通过工单系统（[ticket.example.com](https://ticket.example.com/#/process/related)）申请执行
* **【强制】** 生产MySQL数据库的所有操作只能通过以上两种途径申请操作
* **【强制】** 对大表（大表标准：大于等于**500万**行记录，或表大小超过**3G**）或影响行数超**1万行记录**的操作，包含增减字段、增减索引、修改字段类型等DDL操作，批量UPDATE等DML操作，都需要提前一天与DBA沟通执行可行性，且工单需提前一天申请。同时需确认canal消费是否会积压延迟，与BI沟通是否有影响。
